2026-08-23（`canon/LEDGER.md` 0121）。ユーザー逐語「**カメラ映像で、最初の1-Aだけなぜかちかちかしている**」。
契約は `rules/streaming.md` の「撮像の質と残像」節が正本。ここは**次に同じ訴えが来たときの切り分け方**だけ。

## 結論から: 配信スマホではなく、こちらが足していた色ノイズだった

疑う順が逆になりやすい。「カメラ映像が」と言われると配信側・電波・露出を疑うが、
**この作品は映像の上に自前の「撮像の質」を重ねている**（`feel`）。足した層の方が動いていた。

## 切り分けの 3 手（どれも数分・実機ビルド不要）

### 1. 配信スマホを**直に**引いて測る

Unity も HMD も頭の動きも挟まないので、**カメラの側かどうか**だけが出る。

```bash
curl.exe -m 4 -s http://<ip>:8080/health   # aeLock / awbLock / flicker / iso / expUs
```

映像そのものは `http://<ip>:8080/video`（MJPEG）を Python で引いて、フレームごとの
**明るさと色**を測る。実測（3 台とも）: 色差の隣接差 中央 **0.04〜0.09 / 255** ＝ 動いていない。

⚠ **`/stream` ではなく `/video`。** 端末の HTML の `src` を見れば分かる。

### 2. `feel` を卓から切って走らせ直す（**焼き直し不要**）

`feel` は `_STATE_KEYS` に入っているので `POST /state` で live に配れる。
`{"noiseDark":0,"noiseFixed":0,"agc":0.7,"targetLuma":0.34,"followSec":1.1}` を送ると粒が消える。

⚠ **5 つとも 0 にしない。** `ShowFeelDef.LooksUnset()` が真になって**既定値へ戻る**
（＝ 切ったつもりで切れていない）。`agc` などを残すこと。
⚠ 終わったら `{"feel": null}` で元へ戻す。

### 3. 走行の**生録画**から、明るさと色を**別々に**測る

⚠⚠ **明るさだけ見ても色の明滅は出ない。** 色ノイズは輝度成分を抜いてあるので、
グレースケールにはほとんど乗らない（`work-style.md` §2 の「指標の中で分離しているか」）。

- 区間ごとに、0.4 秒の移動平均を引いた**残差の RMS**を、**明るさ**と **R−B** で別々に出す
- ROI は片眼の中央、**明るい 25% の画素だけ**（まわりの闇を混ぜない）
- ⚠ `_eye.mp4` ではなく **`_raw.mp4`** を使う（変換で落ちる・OOM で変換が失敗しても raw は残る）
- 時刻合わせ: `_xp.log` の行頭の壁時計と `t=` から t=0 の壁時計を出し、
  `meta.json` の `record_started_iso` と引く

実測（1-A / 1-B / 1-C の色の揺れ）: **4.50 / 0.07 / 0.07** ＝ **1-A だけ 64 倍**。

## なぜ 1-A だけなのか

**カメラ A の画がいちばん暗いから。** ノイズの床は絶対値なので、暗い画では信号に対する
割合が跳ね上がる。実測の明るさ **1-A 81 / 1-B 111 / 1-C 153**。
⇒ **「1 つの区間だけ」と言われても、その区間に固有の実装を探す前に「そこが極端な値を取る量」を疑う。**

## 直した中身

`ScreenComposite.shader` の色ノイズ 2 点だけ（**輝度の粒は触っていない**）:
引き直しを 30Hz → **10 フレームに 1 度＋補間**、強さを輝度の粒の 1.6 倍 → **0.55 倍**。
⚠ 混ぜると分散が痩せるので `rsqrt(w²+(1-w)²)` で戻す（戻さないと**粒の強さが 3Hz で脈打つ**）。
