**種フレームを渡した Codex（`-Mode image`）は、部屋の背景をほぼそのまま保つ。**
2026-07-29 の実測（640×480・現地の生映像を種）: 差の平均 6.5/255、閾値 30 を超えるのは画素の **2.5%**、
そこから起こしたマスクの覆う面積は **1.5%**（＝足された人影だけ）。だから
**種と生成の差分がそのまま cue のマスクになる**（`make-diff-mask.py`）。

**Why:** 設計レビューは「生成物は似た別の部屋になり、差分マスクは全面白へ収束する」を最大の懸念に挙げた。
実際に 4 枚作って測ったら成立していた。ここを測らずに設計を降ろすと、逆に「動画生成の外部ツール併用」へ
無駄に戻ることになる。

**How to apply:**
- 入力画像は**プロンプトの中に絶対パスで書く**（`codex-run.ps1` に入力画像の引数は無い）。読ませるには
  そのパスが `-Cwd` か `--add-dir` の下にある必要がある
- サーバ経由（`POST /generate`）は作業ディレクトリを**リポジトリ外の temp** に固定し、種フレームを
  そこへコピーしてから渡す（image モードは Cwd へ書き込み権を与えるので、show.json のある場所を渡さない）
- 生成できるのは**卓を動かしている PC からだけ**（`/generate` は 127.0.0.1 以外を 403）。卓は 0.0.0.0 で listen している
- 背景が同じでも**生成のゆらぎ**で棚や床まで差が出る。マスクは `--roi` で領域を絞るか
  最大領域だけ残す（`--keep-all` を付けない）
- Codex が出せるのは**静止画だけ**。動く素材（i2v）は従来どおり外部ツール

## 生成の入出力でトーンを往復させる（2026-08-15・`tools/gen-tone.py`）

**種フレームは明るい部屋のままモデルへ渡していた。** 暗くするのは実機の post（合成のいちばん後ろ）
なので、**生成モデルは暗い画を一度も描いていなかった**。実測（カメラ A の種）:

| | 平均輝度 |
|---|---|
| 生成に渡していた種フレーム | **122.9** |
| 実機で体験者が見ている画（post 100%） | **48.2** |

暗所の人形は暗いだけでなく陰影の付き方が違う（光源の向きが読める・輪郭が闇へ沈む・顔の一部だけが
光を拾う）ので、後段の露出調整では作れない。ユーザー指摘「明るい部屋で生成されて追加された人形は、
ホラーっぽくなくリアルでもなく CG っぽい」の機序（`canon/LEDGER.md` 0050）。

    種フレーム → dim → 生成 → undim → captures/ へ保存 → 実機で post

**Why 暗いまま保存しないか**: cue の素材は「そのカメラが撮ったならこう写る生映像」の位置に入る。
暗いまま置くと ①実機で post が二重に掛かる ②半分マスクで境目に段差が出る（画面の左右で撮像特性が
違う ＝ 装置が 2 台あることになる）③`LEDGER` 0020「人形を合成したあとに他の全ての画像処理を」と
`rules/streaming.md`「合成はポスト FX の前。浴びないと必ず浮く」に反する。

**How to apply:**

- 卓の 🪄 は**自動で往復する**（`capture-server.py` の `_gen_run`）。人が触るのは生成だけ
- 手で回すなら `py -3.11 tools/gen-tone.py dim|undim|check|sweep <in> <out> --scale 1.0 --cam A`
- 式と順序は `shaders.js` の FS_POST ＝ Unity の `ScreenComposite.shader` と同じ
  （ヴィネット → 露出 → 色温度 → 色かぶり → コントラスト → 黒浮き → 彩度）。undim はその逆順・逆演算
- **`--scale` は実機の post をどれだけ掛けるか**。1.0 = 実機と同じ暗さ。往復の実測は
  平均誤差 1.2 / 最大 24 / 潰れ 0.65%（scale 1.0）なので、**1.0 で往復できる**
- ⚠ **clamp した所は戻らない。** 生成物に暗部が増えると潰れも増えるので、
  `check` の「潰れ」と「往復の誤差」を見てから scale を決める

⚠ **素通しに黙って落ちない。** トーンが失敗しても生成は続ける（1 枚 60〜150 秒を捨てないため）が、
`job['tone']` に必ず残し、卓が「⚠ 明るさの往復が素通し」と赤で出す。黙って素通しにすると
「生成が下手になった」ようにしか見えない。

⚠ **Pillow 12 で `ImageMath.eval` は削除された**（10.3 で非推奨 → 11 で削除）。`lambda_eval` は
「dict を受け取る関数」を渡す形で、`min` / `max` は**第 1 引数が画像**でないと通らない。

関連: [[web_compositor]] / [[material_flow]]

## ⚠⚠ 生成の色ずれは「プロンプトで直すもの」と「倍率で直すもの」に分かれる（2026-08-15 実測）

4 周目 A の「左半分に大量の人形」を 3 回作らせて分かったこと。
**測るのは暗い空間のまま**（`dim` した種と、生成の出力を直接比べる）。undim を挟むと、
往復のせいなのか生成のせいなのかが混ざる。

### プロンプトで直る — 片側だけの塗り直し

1 回目は「明るさを変えない」とだけ書いた。結果:

  右半分 … 種 83.0 → 出力 83.0   **完全に一致**
  左半分 … 種 98.2 → 出力 63.2   0.64 倍。しかもコントラストが 26% 潰れた

右が完璧だったのは、そこにだけ **「1 画素も変えない」** と書いていたから。
左には「明るさを変えない」という抽象的な言い方しかしていなかった。

⇒ **同じ強さの言い方を、直してほしい側にも使う。** 2 回目に
「人形と接地影以外は、左半分も入力の画素をそのまま残す」「カーテン・壁・床・棚は
1 画素も塗り直さない」と書いたら、**左右の食い違いが消えた**（左 0.888 / 右 0.882）。
⇒ **測った数字をプロンプトに書く。** 「左が 98.2 → 63.2 になっている」と具体的に伝えるのが効く。

### プロンプトでは直らない — 絶対的な明るさ

同じ調子で「12% 暗いので 1.13 倍に戻して」と数字で頼んだら **1.75 倍**になった。
3 回の推移は **0.64 → 0.88 → 1.75**。編集モデルは毎回描き直すので、露出を狙って当てられない。

⇒ **一様なズレになったら、そこで打ち切って倍率で合わせる。** オフセットは足さない
（黒が浮いて「薄い」画になる。実測: gain 0.94 + offset +55 で最暗部が 40 → 73 に浮いた）。
倍率だけなら平均が一致し、白飛びも 0%。**倍率で直してよいのは「一様」になってからで、
片側だけ暗い状態を倍率で殴ってはいけない。**

### 直しをどこに置くか

⚠⚠ **cue の `hasMatch` / `matchGain` には入れない。** あそこは卓が `bakeColorMatch` で
書く場所なので、素材工房や cue エディタで保存し直した瞬間に消える。しかもこれは
「素材を実写へ寄せる」補正ではなく「生成の露出を戻す」補正で、素材自身の性質。
**画像そのものに焼いて、生のままの生成物は `_raw.png` で残す。**

### 判定は画面に出る形で見る

数字だけでも絵だけでも足りない。**左＝生成 / 右＝プレート**に組んだ 1 枚を作って、
継ぎ目のカーテンが繋がって見えるかを目で見る。今回はそれで採否を決めた。
