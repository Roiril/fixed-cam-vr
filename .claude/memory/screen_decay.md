# 周回で進む解像度の劣化（装置が痩せていく）

出どころは `canon/LEDGER.md` 0012（2026-08-12）。**周を重ねるごとに映像の解像度が落ちる。
1 周目の入口は今のまま、3 周目はだいぶ粗い。段差は作らない。**

## 何を触ると壊れるか（先に読む 4 つ）

### 1. これは post ではない。post に足してはいけない

post 12 項目（`_Pixelate` を含む）は **shader / 卓の FS_POST / common.js / pipeline.js の
4 箇所を手作業で同期**していて機械テストが無い。そこへ時間の関数を持ち込むと必ず沈黙して食い違う。
だから `_NoiseDark` / `_Echo` / `_Glitch` と同じ**別系統 uniform・単一 writer**の枠に入れてある。

| | |
|---|---|
| uniform | `_CoarseBlocks`（枠を横切るブロック数。**0 = 無効**）/ `_CoarseSoft`（境目の渡し方） |
| 唯一の writer | [`CameraFeelFx`](../../Assets/Scripts/Streaming/CameraFeelFx.cs) |
| 進みを決める | [`ScreenDecayLogic`](../../Assets/Scripts/Streaming/ScreenDecayLogic.cs)（純ロジック・dt 注入） |
| 回すのは | [`ShowRunDirector`](../../Assets/Scripts/Streaming/ShowRunDirector.cs)（相と周回を持っている唯一の場所） |

⚠ **卓のプレビューには出ない**（`feel` と同じ扱い。実機だけが持つ「装置の挙動」）。

### 2. ブロック数の対応表は C# にしかない

シェーダに `0..1 → ブロック数` の式を書くと、テレメトリのために C# 側にも同じ式が要って
2 箇所になる。だから **C# が解いた「ブロック数」をそのまま渡す**。
シェーダは量子化するだけで、進み 0..1 を知らない。

```
ScreenDecayLogic.BlocksFor(progress)   // 900 → 110 を等比で
```

等比なのは、等差だと**最初の 1 周で見た目が全部落ちて後の 2 周が動かない**から
（900 → 110 を等差で割ると 1 周目で 900→637、3 周目は 373→110。目に映る変化量が桁違いにずれる）。

周の境目での値（枠 / 映像の領域は ×0.75 ＝ 4:3 が 16:9 の枠へ letterbox される分）:

| | 枠 | 映像の領域 | ソース 640px あたり |
|---|---|---|---|
| 1 周目の頭 | 900 | 675 | 0.95 px/ブロック（＝何も起きない） |
| 2 周目の頭 | 447 | 335 | 1.9 |
| 3 周目の頭 | 222 | 166 | 3.9 |
| 3 周目の終わり〜帰りの A | 110 | 82 | 7.8 |

### 3. 段差を作らない仕掛けは 3 つ。1 つでも外すと階段になる

1. **周の中も進む** — `(lap-1 + 経過/LapRefSec) / totalLaps`。周の頭で飛ばない
2. **単調** — 下がらない（下がると「直った」に見えて装置の劣化という筋が壊れる）
3. **上げ幅の頭打ち** `MaxRisePerSec`（0.035/秒）— 速く歩いて周が飛んでも滑って渡る。
   自然な進みは 1/90 ≈ 0.011/秒 なので、3 倍までは許して段差だけ潰す形

⚠ **進むのは `Run` 相だけ。** 導入と終了では**値を保持する**（0 に戻さない）。
終了で 0 へ戻すと**終わった瞬間に画が急に鮮明になる**（暗転前に演出を見せ切る猶予がある）。
落とすのは `ShowRunDirector.BeginRun()`（体験者の交代）1 箇所だけ。

### 4. モザイクではなく「低い解像度で引き伸ばした画」

境目を硬く切ると**モザイクを掛けたように見える**（＝加工した、が伝わる）。
`_CoarseSoft` はブロックの境目を smoothstep で渡す幅で、1 サンプルのまま bilinear 相当の
にじみを作る（4 タップ引くと `SampleBase` が 4 倍になり Quest の予算に乗らない）。

⚠ **量子化を 2 回重ねない。** 著作した `_Pixelate` と `_CoarseBlocks` は
**粗い方だけ**を掛ける（`min`）。両方掛けると 2 つの格子が干渉して、
どちらでもない縞（モアレ）が出る。

## ⚠ この演出は 2026-08-06 の設計判断を覆している

`rules/streaming.md`「やってはいけないこと」に**「周回で単調に劣化させない」**と書いてある。
理由は「一番見せたい 1 周目の自分（3 周目の背景に流れる録画）が一番見えなくなる」。
2026-08-12 にユーザーが正面から覆した（LEDGER 0012）ので実装したが、**懸念は消えていない**。

- 録画（`_OverlayTex`）もライブと同じ `sampleUv` で引くので**同じだけ粗くなる**。
  これは仕様として正しい（装置を通して見ている以上、録画だけ鮮明だと切替がばれる）
- 危ないのは**終端の値**。3 周目に人型と「手を上げていない」が読めなくなったら
  `ScreenDecayLogic.EndBlocks` を上げる（110 → 150 で映像の領域が横 112）

## 見る手段

**シェーダの誤りは `unity.ps1 test` に 1 件も出ない**（この codebase は同じ型で 3 回踏んでいる）。
合成プレビューに進みを注入できるようにしてある:

```powershell
.\tools\unity.ps1 menu composite -Set decay=0.66
```

`decay` を入れると出力の名前に `_d066` が付くので、0 / 0.33 / 0.66 / 1.0 を並べて見られる。
**人形が入った絵で見る**こと — プレートだけでは「人型が読めるか」を判定できない。

## 観測（実機）

`ShowTelemetryHost` のサマリ行に 3 つ。**「進みが動いた」ではなく「画に出た」を見る**ため、
値と一緒に**書く先を掴めたか**を出している。

| キー | 意味 |
|---|---|
| `coarse` | 進み 0..1 |
| `cbx` | 実際に書いた枠のブロック数（0 = 量子化していない） |
| `coarseMat` | 書く先（スクリーンの Renderer）を掴めたか。**0 なら進んでも 1 画素も変わらない** |

`analyze-xp-log.py` の「効果の実在」節が、①書く先が無い ②本編に 10 秒以上居るのに進んでいない
③導入の時点で既に落ちている ④1 標本（約 2 秒）で 0.09 以上跳ねた（＝段差）の 4 つを判定する。
**C# と Python は対で直す**（片方だけだと沈黙して食い違う）。
