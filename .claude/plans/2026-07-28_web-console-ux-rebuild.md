# オペレータ卓の UI / UX 立て直し（思想・情報設計・デザインシステム）

## 概要

ユーザー依頼（2026-07-28）:「**UI の全体的なクオリティ、UX アップ。設計から思想まで**」。

対象は **廻リ視（fixedcam）の Web オペレータ卓 `tools/web-compositor/`** に確定。
HMD 内 UI（`StatusHud` / `ControllerGuidePanel`）は 2026-07-20 の staff-input-hud-redesign で
単一サーフェス化済みで構造的破綻が無いため、今回は対象外（点検のみ実施）。

独立した design-critic 4 体（情報設計 / ライブ運用 / 著作フロー / デザインシステム）を並列で走らせ、
シュビー本体がブラウザ実測（DOM 計測）で裏取りした。**4 体が独立に収束した論点**を最重要とみなす。

## 思想 — 3 つの原則

現状の卓は**機能の陳列棚**になっている。個々の機能は思想を持って作られており、README には
本番安全装置の一覧まである。壊れているのは機能ではなく、**画面の構造が作者の作業の構造を写していないこと**。

### 原則 1: 画面の並び順 = 依存の順序

ゾーンが無ければ区間が無い。ラインが無ければ `at:"line"` が選べない。較正が無ければ CG 人形が出ない。
**この依存はすでにコードの中に厳然として存在し、`ribbon.js` は選択肢を塞ぐ形で実装済み**
（担当ラインが 1 本も無ければ「ライン通過」を選ばせない）。にもかかわらず画面上では、
その前提（較正・姿勢・ゾーン・ライン・部屋）が演出より**下**か**別モード**に置かれている。

→ **依存の順序を画面の順序にする**。作者は上から下へ進めば、必要なものが必要な順に出てくる。

### 原則 2: 説明文ではなく状態で導く

3,381 字の hint は「順路が構造に無いこと」の代償として書かれている。順路を構造にすれば説明は不要になる。
UI に残す説明は **1 行のサブタイトル**だけ。あとは **空状態・disabled の理由・完了バッジ**が語る。

この作法にはプロジェクト内に先例がある（`ribbon.js:849-868`：担当ラインが無ければ選択肢を disable し
`title` に理由を書く／2026-07-27「作れない組み合わせは卓が選ばせない」）。**新しい思想ではなく、
既にある思想を全面へ展開する**だけ。

### 原則 3: 本番面は「見る」と「押す」だけ

ライブ運用に著作用の要素（画質スライダ・📐 姿勢欄・🎯 較正・カメラ追加）を出さない。
本番で必要なのは **3 つの真実**（誰が画面を握っているか / カメラは生きているか / 体験者はどこにいるか）と、
**1 つの操作**（画面を取り返す）。それ以外は降格する。

## 段 0 — 壊れているものを直す（設計と独立・即時）

いずれも決定論的に確認済み。設計変更を待たずに実施する。

### 0-1. `■ 演出を止める` が本番の演出を止められない（critical）

**事実**:
- 卓の `■`（`app.js:997`）・`⛑ 全部解除`（`app.js:174`）・`🚶`（`app.js:996`）は
  `stopCue`（`control.activeCue=""`）と `setCameraOverride:null` の 2 コマンドしか送らない
- タイムライン発火の演出（Take）は `activeCue` を**使わない**（空のまま走る）
- `ShowControlClient.cs:1292-1296` は `liveSuppressed = activeCue非空 || override非空` を計算し
  `TakeRunner.SetSuppressed` へ渡す。`SetSuppressed(true)` の時だけ走行中の演出を畳む（`TakeRunner.cs:145`）
- したがって `stopCue` は `false → false` で **no-op**
- 皮肉にも「📺 カメラ固定 → 🚶 解除」の 2 段だけが実際に畳む（UI のどこにも書かれていない）
- 同じ穴は 2026-07-23 に Quest のグリップ操作でのみ塞がれた（`ShowControlClient.cs:1498` のコメントが穴を明記）

**修正方針**: `runEpoch` と同じ流儀で **`control.takeAbortEpoch: int`** を追加する。
コマンドは状態の変化としてしか Unity へ伝わらない（long-poll モデル）ため、
「既に空の値を空にする」形の停止は原理的に伝わらない。カウンタの増分なら必ず伝わる。

- Web: `POST /command {type:"abortTake"}` → `capture-server.py` が `takeAbortEpoch++`
- Unity: `ShowControlClient` が変化を検知 → `TimelineDirector.AbortActive()` → `TakeRunner.CleanupActive()`
- `■` は改名して **「画面を取り返す」**とし、`stopCue` + `abortTake` を両方送る
- `⛑ 全部解除して自律へ` にも `abortTake` を含める
- 既存契約は不変（フィールド追加のみ・古い Unity は無視して従来動作）

### 0-2. ライブモードで緊急操作が画面外

`style.css:858-859` は author / atelier でのみ `.multicam { order: 9 }` を指定し、**live で指定漏れ**。
live 用の横並びレイアウト（`style.css:1253-1256`）は作り込まれているので、意図ではなく漏れ。

→ ライブでも監視列を下げ、`✅ 本番前チェック` と緊急バーを最上部へ。緊急バーは `position: sticky; top: 0`。

### 0-3. `.global-fx` の枠線が描かれていない

`style.css:516` が未定義変数 `--line`（正しくは `--line-soft`）を参照。CSS は無効 var() を含む宣言を
丸ごと破棄するため、**枠が存在しない**。同時にファイル唯一の 6px 角丸（規約は角丸ゼロ）。

### 0-4. 他カメラの素材をカットに割り当てられてしまう

マスクは**カメラの構図に対して**焼かれる（`atelier.js:589-596`）ので、B の cue を A のカットに付けると
実機で位置が合わない。にもかかわらず `ribbon.js:1221-1223` は全カメラの cue を無差別に列挙する。
**絞り込み関数 `cuesForCam` は書かれているのに、どこからも呼ばれていない**（`ribbon.js:171` デッドコード）。

→ 原則 2 の作法（作れない組み合わせを選ばせない）をここへ延長する。
他カメラ分は optgroup「他カメラ（構図が合いません）」へ落として無効化。既存データが他カメラを
指していたら `stepIssue` で警告。

## 段 1 — 構造（モードを作業の順路にする）

### 1-1. ナビを 5 段へ

| # | モード | 中身 | 現状からの移動 |
|---|---|---|---|
| ① | **📍 場所** | フロアマップ全 6 モード + 🎯 較正 + 📐 姿勢 + 💡 照明 + 📡 発見 + 🩺 診断 | **新設**。author / live / 常時表示に散っていたものを集約 |
| ② | **🧪 素材** | 素材工房（現状のまま） | 据え置き。生映像は工房内に持つ（監視列への依存を切る） |
| ③ | **🎬 演出** | リボン ｜ シミュレータ（左右 2 面）+ 🎵 BGM + 🎭 人形 | フロアマップとカメラ列を外に出す |
| ④ | **📦 焼き込み** | エクスポート | 独立（未保存ガードは既に正しく効いている） |
| 🚨 | **本番** | ✅ チェック → 緊急バー(sticky) → 監視列 → ラン状態 | 並びを反転 |

判定基準は 1 つ：**この作業は、会場でカメラと部屋が目の前にある時にしかできないか**。Yes → ①。

フロアマップが ① と ③ の両方に現れるのは分裂ではない。**編集（①）と参照（③・🚶 歩かせるだけ）で
別の顔を出す**のが正しい。現状は 6 モードを 1 セクションに詰めているので顔が 1 つしかない。

### 1-2. カメラ列を 3 部品に解体する（`data-group` 欠落の根治）

現状の `.multicam` は 1 部品で 6 役（生映像 / Quest 実映像 / 9 スライダ post / 📐 姿勢 + 🎯 較正 /
接続・pin・手動 IP / role セレクト）を担っており、**どのモードにも属せないので「常時表示」に逃げた**。
CSS はその代償を `order: 9` と `:not(.active) .col-sec:nth-child(3)` という位置ハックで払っている。

| 部品 | 中身 | 所属 |
|---|---|---|
| `CameraMonitor` | 生映像 / Quest 実映像 / 接続 / 📺 切替 / 📷⏺ | ① 場所 + 🚨 本番 |
| `CameraSetup` | 接続・📌 pin・緊急手動 IP・role・📐 姿勢・🎯 較正 | ① 場所のみ |
| `CameraGrade` | 9 スライダ + 🎥 全体グレーディング | ③ 演出のみ（本番では読み取り専用表示） |

これで全部品に `data-group` が付き、位置ハック 2 件が消える。
ライブ中の「触れるように見えて触れない」35% 減光（`fx-locked`）も不要になる。

### 1-3. 序列を構造に入れる

- `.mc-title` → `<h2>`（機械可読・目次生成可能）
- 第一級（リボン / 本番前チェック + 緊急 / フロアマップ + シミュレータ）と従属物（BGM・エクスポート・人形）で
  視覚重量を変える。**現状は全部が muted なので、格上げではなく「格下げの余地を作る」作業**
- 緊急バーは `position: sticky; top: 0`

### 1-4. hint を 3 つに割り、2 つを UI から追い出す

| 種類 | 行き先 |
|---|---|
| ①この場所は何か（40 字以内） | **残す**。1 行サブタイトル・畳まない |
| ②どう操作するか | **空状態と disabled の理由へ**（原則 2） |
| ③なぜそう設計したか（不変条件・禁止事項） | **README / plan へ**。見出しの `?` からアンカーで開く |

一括トグル（`app.js:789-813`・localStorage キー 1 個で全 14 セクション同時開閉・既定で畳む）は廃止。
移行期のみセクション単位の `<details>`（記憶キーもセクション単位）。

**順序は「移す → 消す」**。先に消すと現場の知識が失われる。

## 段 2 — 環を閉じる（著作フロー）

### 2-1. 「確定」と「配信」を割り、シミュレータを編集バッファへ繋ぐ（最優先）

現状 `show-sim.js:730` は**保存済み show.json しか読まない**。リボンは未保存中 `adoptState` をスキップする
（`ribbon.js:1761`）ので、両者は静かに乖離する。結果、演出を 8s→4s に直して確かめる作業が
「💾 保存（＝この瞬間 Quest へ配信）→ スクロール → 🚶 → 歩く」になる。
**リハで Quest を繋いだままなら、試行錯誤が全部体験者側の画面へ流れる。**

根本原因は `show.json` 1 本が**編集バッファ・配信チャネル・永続形式**を兼ね、💾 が「確定」と「配信」の
2 つの意味を持っていること。

→ シミュレータの deps に `getDraft` を足し、リボンがメモリに持つ timeline（`ribbon.js:101`）を
`serializeTimelineV3` して渡す。これで「編集 → 検証」から保存が消え、💾 は「Quest へ配る」意味に純化する。
`● 未保存` の文言も「**まだ実機に配っていない**」へ改める。フロアマップの layout も同様。

### 2-2. リボンにプレイヘッドを付ける

シミュレータが毎 tick 持つ (lap, camera, 発火 take id, 経過秒) をリボンへ push し、
該当区間に `.playing` と縦線を描く（レーンは既に秒→px 換算 `PX` を持つので線 1 本）。
逆向きも作る：リボンの区間クリックでその区間の入口から走らせる（「この区間だけ試す」が 1 クリック）。

author モードで `timeline-sec` と `sim-row` を隣接させる。

### 2-3. 著作側の警告を 1 箇所に集約

`preflightRows` の後半（タイムライン・演出素材・BGM・未保存）は現場ではなく著作の話。
著作行だけ抜いてリボンのツールバー下に `⚠ 3 件` として常設し、クリックで該当区間へジャンプ。
ここに `takeIssue` と `takeTimingRisk`（滞在時間より開始が遅い＝山場が出ない）を集約する。

計画 2026-07-25 §4 が「作者が『山場が出ない』危険に気づく唯一の手段」と位置づけたものが、
**いまは気づきに行かないと見えない**。

### 2-4. フロアマップに undo を与える

`floormap.js` に undo は 1 つも無い（grep 0 件）。「全消去」は確認なしで 144 タイルを消し、
「cuts から自動生成」は塗りを丸ごと上書きする。唯一の砦の `.bak` は **postState のたびに上書き**され、
画質スライダは 140ms デバウンスで postState を打つ。
→ **塗りを壊して保存 → 画質スライダを 1 回触る、で復旧手段が消える。**

対処:
- `ribbon.js:118-140` のスナップショット undo を移植（`common.js` へ `createUndo` として共通化）
- サーバ側は `layout` / `timeline` を含む変更のときだけ別枠バックアップ（post スライダの連打で失われない）

## 段 4 — 本番面の堅牢化

### 4-1. 鮮度を一次指標に昇格

現状の `● LIVE` は `<img>` の `load` で true、`error` でしか false にならない
（`app.js:389-401`）。`capture-server.py` の `_proxy_cam` は upstream 断を握り潰して正常終了するので、
**スマホが熱落ちしても `error` が飛ばない**。→ 最後のフレームを表示したまま `✅ 全台 LIVE 受信中`。

→ `load` ごとに `lastFrameAt` を刻み、2 秒無更新で `⏸ 停止 3s` へ。`🩺` は 30 秒毎に自動実行し、
ボタンは「詳細を開く」に降格。**診断は押すものではなく、常に出ているもの**にする。

### 4-2. ラッチを列挙関数に統一

現状バー・プリフライト・⛑ の 3 箇所が独立に `cameraOverride` / `activeCue` の 2 つだけを見ている。
show.json に永続する他のラッチが漏れている：

- `control.slots`（bindSlot）— `▶ ラン開始` が消さない → **前の体験者の顔で生成した素材が次の演出に出る**
- `control.discoveryEnabled=false` / `autoFollow=false` — 昨日の切り分けで切ったまま翌日も無効
- `cameras[].pinned` — 手動 IP 固定が残り自動追従が死ぬ
- `lap > 1` — 前の体験者の周回のまま次を始めても全緑

→ `latches()` が配列を返し、**バー・プリフライト・⛑ が同じ配列を消費**する。
`⛑` ＝全部戻す、`▶ ラン開始` ＝ `⛑` + `runEpoch++`。追加漏れが構造的に起きなくなる。

### 4-3. 「ゾーン（人の居場所）」と「画面（映っているカメラ）」を分離

heartbeat の `cam` は `registry.ActiveIndex`＝**画面のカメラ**。演出のインサートでカメラ D が映っている間、
卓は「ゾーン D」と表示し、その index で区間を引くので「次の演出」まで別区間の内容になる。
正しい `currentZone` は送信済みだが、読者は `floormap.js:1863` だけで、その floormap は
**ライブモードでは非表示**。→ 本番中に体験者の物理的な居場所を見る手段が画面上に存在しない。

→ フロアマップを本番面へ読み取り専用で昇格し、2 ラベルに分離する。

### 4-4. 「いま画面を握っているのは誰か」を第一級指標に

`自律 / 演出〈名前〉残り 4s / 卓が固定 C / 手動 cue` の 4 状態を 1 行で。
heartbeat に走行中の `takeId` を追加。段 0-1 の `abortTake` と対になる。

### 4-5. 本番前チェックの偽陽性を潰す

- Quest が**位置合わせモード(REG)でも ✅** になる（`app.js:1044-1049`）
- `lap > 1`（前の体験者の続き）を検査しない
- OS recenter で立つ `CourseFrame.NeedsReRegistration` が **heartbeat に載っていない**
  → 「歩いても切り替わらない」の最有力原因が本番前チェックの守備範囲の外

## やらないと決めたこと

4 体すべてが独立に警告した「一般論としては良さそうだが、この道具では害になる」もの：

- **確認ダイアログの増設** — 暗所・緊張下では読まずに Enter になる。既存の `▶ ラン開始` の `confirm()` も外し、
  **可視ラッチ + undo + 押下後の状態表示**で担保する（現行の `#latchBar` / `Ctrl+Z` / `.bak` の方針が正しい）
- **ウィザード化・一方通行のステップ UI** — 現場の最頻操作は「較正だけやり直す」「ラインを 1 本引き直す」。
  順路はタブの順序と完了バッジで示し、どの段へもいつでも入れる状態を保つ
- **自動保存** — 💾 が Quest への配信を兼ねている以上、自動保存は「編集途中が体験者に配られる」と同義
- **オンボーディング・ツアー・ツールチップ巡回** — 利用者は 1 人。空状態への投資が同じ効果で永続する
- **自動化の追加**（自動ラン開始・自動ラッチ解除・自動張り替え）— これ以上増やすと
  「勝手に何かした」を人間が疑い始めて診断が不能になる。discovery 自動追従が境界
- **light テーマ / テーマ切替 / CSS フレームワーク導入 / モバイル対応の深追い** — 暗所固定・PC 固定・1 人用
- **本番中のアニメーション** — 暗順応した目に動きは疲労と誤検知を生む。起動時 1 回の `fadeIn` まで
- **余白を増やして読みやすくする** — 1 画面主義が壊れる。読みやすさは**サイズの段を減らして**得る
- **卓で CG 人形を実描画する** — 一致を検証する手段が無い（設計が既に正しく結論済み）。輪郭プロキシのまま
- **hint を短くするだけの改修** — 情報は消えるが順路は生まれない
- **全画面オーバーレイをインラインへ畳む** — 映像画素を指す作業は大きいほど正しい。
  原則を明文化して**両方を大きくする**方向が正（🎯 較正・📍 立ち位置＝全画面 / マップ・タイムライン＝インライン）
