# 導入 — 現実が映像になる（パススルー → 2D スクリーン）

体験の最初、体験者が HMD を被ってから本編（3 周）に入るまでの約 33 秒。
**現実そのものを「固定カメラの映像」へ格下げし、格下げが完了した瞬間、その映像の中に自分が居る。**

企画書（[docs/proposal/](../../docs/proposal/)）の導入は「区間 1 を固定視点下で歩いて慣れる」だけで、
この遷移演出は**企画書に無い新規追加**。3 分の予算を食う点は明示のトレードオフ（§3 の尺表）。

---

## 1. 決めたこと（と、なぜユーザーの案をそのまま採らなかったか）

出発点はユーザーの案「パススルー → 3D のメッシュだけの VR 世界 → 幽体離脱 → スマホの位置まで行って
スマホに入る」。独立した 2 体でそれぞれを最善まで詰め、技術可否を実パッケージのソースで確定させた結果、
**視点を動かさない形を骨格に採る**。案の核心（現実からの離脱感）は捨てず、離脱の対象を差し替える。

### モチーフの対応表

| ユーザーの案 | この設計 | 差し替えた理由 |
|---|---|---|
| 3D のメッシュだけの VR 世界 | **そのまま採る**。ただし CG のワイヤーではなく**パススルーの輪郭線表示**で作る | `edgeRenderingEnabled` が実行時に使える。**現実の輪郭**なので自分の手も線になる。CG より説得力があり、実装も軽い |
| 幽体離脱（視点が身体から離れる） | **「現実の身分が落ちる」に置換**。視点は 1 度も動かさない | 離脱感の正体は「自分が自分の外にある」こと。視点を動かす代わりに、§4 段 5 で**外から自分を見せる**ことで同じ場所に着く |
| スマホの位置まで飛ぶ | **落とす** | 床 1.8m 四方では飛行距離が **1.5〜2.5m** しか取れず「飛んだ」ではなく「寄った」に見える。物理制約で埋まらない（詰めた側が自ら認めた弱点） |
| スマホに入る | **「スマホから見られる」に反転** | 本編は「カメラから見られた自分を見る」体験。導入で一度中に入ると、本編で外から見る側に戻るときにねじれる。**向きを逆にすると 3 周目の反転（追ってきた人形が自分だった）の伏線になる** |

副産物として 2 つ消える。**ガーディアン表示**（現行 SDK では `OVRBoundary.SetVisible` が非推奨で
コードから消せない）と、**VR 酔い**。床 1.8m 四方で体験者は常に境界の近くに立っている。

### 骨格の一文

> 視点は動かさない。動かすのは現実の側の身分（現実 → 映像）。
> 格下げが完了した瞬間、枠の中に自分が居る。

## 2. 3 周目との接続 — 「右手を上げる」を専用の作法にする

**この設計の最重要点。** 導入は伏線を張れる唯一の場所で、張る先は企画書の最終目的（3 周目の反転）。

- **導入（段 5）**: 枠の中にカメラ映像が出た直後、体験者は**右手を上げる**。画面の中の自分も上げる。
  → 「画面の中のあれは自分か？ → 手を上げて確かめる」という**確認の作法**を体に覚えさせる
- **3 周目**: 背景は 1 周目の録画。画面の中の人物は**過去の自分**なので、いま手を上げても**上がらない**。
  → 言葉の説明なしに「あれは自分ではない」が成立する

### 3 周目でその動作を誘発する手段（アドバイザー指摘の穴）

導入は画面の中の自分が鏡として誘えるが、3 周目は誘い水が要る。**CG 人形が先に右手を上げる。**

- 3 周目の演出のカットで、CG 人形に「右手を 1 回上げる」動作を入れる（体験者の手への追従とは別の、
  スクリプトされた 1 回）
- 体験者は「人形が自分の動きを真似た？」と思い、確かめるために自分の手を上げる
- → **人形は追従して上がる**（実際は体験者の手に追従している）／**画面の中の過去の自分は上がらない**
- 同じ瞬間に「人形＝自分」と「映像の中の人物＝自分ではない」が両方確定する

⚠ 実装上の注意: `ActorArmLogic` は手が取れない間 idle へ合流する仕組みしか持たない。
「1 回だけ腕を上げる」はカット側の指示として新設が要る（§6）。

### 手を上げたことは検出しない

導入も 3 周目も、**体験者が実際に手を上げたかを機械が判定する必要はない**。

- 導入: 画面の中の自分は勝手に映っている（カメラが写しているだけ）。上げなければ伏線が張られないだけ
- 3 周目: CG 人形は体験者の手に追従している（既存の `OvrHandTrackingBridge` → `ActorArmLogic`）。
  上げれば上がるし、上げなければ何も起きない

検出を入れると「上げたと判定されなかった」失敗モードが生まれる。**入れない。**
体験者はコントローラを持たないので、入力としても扱わない（[unity-vr.md](../rules/unity-vr.md) の右手 4 入力とは無関係）。

### 録画への混入は起きない（保証）

導入は `CueScheduler.SetShowGate(false)` の内側で、**端末内録画はゲートで止まっている**。
したがって「導入で上げた手が 1 周目の録画に写り、3 周目でも上がってしまう」事故は構造的に起きない。
ゲートを触るときはこの保証を壊していないか確認する。

## 3. 尺の予算

| 区間 | 秒 | 根拠 |
|---|---|---|
| 導入・演出（段 0〜5） | **33** | 本設計 |
| 導入・慣らし歩行（段 6） | 20 | 企画書の導入本体（`run.introMinSec` の既定値） |
| 本編 3 周 | 90 | 企画書「各周およそ 30 秒」 |
| 終了（見せ切り + 暗転） | 15 | `ShowRunLogic.MaxEndHoldSec` = 12s + フェード |
| **合計** | **158** | 企画書「導入を含め 3 分以内」= 180s に対し **余裕 22 秒** |

**演出の上限は 40 秒**（`run.intro.maxSec`）。超えたら段を飛ばして枠を出す。
薄く保つのが正しい — 導入が体験時間の 1/3 を超えると、3 周目の反転を見せ切る余地が消える。

## 4. 段ごとの設計

体験者は**区間 1 の入口の床の × 印**（`layout.regPoints` の 1 点）に立ち、カメラ A の方を向いている。

| 段 | 尺 | 体験者に見えるもの | 次へ行く合図 | 体験者の状態 |
|---|---|---|---|---|
| **0 暗転** | 0–4s | 黒（既存 `StartupFader`）→ 明けて素のパススルー | **スタッフの明示操作**。落ち着いたかは人間しか判定できない | 立つ。周りを見てよい |
| **1 現実** | 4–8s | 現実そのまま。自分の手も壁も三脚のスマホも実物として見える | 時間 | 何も指示しない |
| **2 格下げ** | 8–16s | 色が抜け、コントラストが上がり、**実物の輪郭が白く浮く**。粒状感と走査線が乗る | 時間（線形ランプ） | 静止 |
| **3 構造** | 14–20s（段 2 と重ねる） | 輪郭だけの世界に、**カメラ 3 台の位置の印**と壁・床の線が加わる | 時間 | 静止 |
| **4 枠** | 20–25s | 周縁から黒が寄せ、正面に長方形が残る。**中はまだパススルー**（現実が枠に閉じ込められる） | 頭の角速度が小さいことを確認してから開始。**枠は開始時点の頭 yaw に出す** | 静止 |
| **5 すり替え** | 25–33s | 枠の中がカメラ A の映像へ。**乱れを 1 回重ねて継ぎ目を隠す**。枠の中に自分が居る。**右手を上げる** | 枠が視野中心 ±25° に 0.5s 継続 **かつ** カメラのフレームが新鮮 | 右手を上げる |
| **6 慣らし** | 33–53s | 本編と同じ画。区間 1 を歩く | `run.introMinSec` の計時をここから始める | 歩行開始・右手を壁へ |

### 段ごとの設計判断

**段 1 は何も演出しない。** 4 秒間ただ現実を見せる。ここを削ると段 2 の変化が「変化」として読めない。
比較対象を先に置くための時間。

**段 2 の順序は 色 → コントラスト → 輪郭 → 粒**。一度に全部動かすと「ただ壊れた」に見える。
順に足すと「質感が落ちていく」過程として読める。**絵は動かない**（視点も対象も静止）ので、
変わっているのは質感だけだと分かる。

**段 3 のカメラの印には数字も文字も出さない。** 出すと較正画面に見える。線は細く、段 2 と同じイージングで
出し入れする。ここは「自分がどこから見られているか」を知る段で、情報表示ではない。

**段 4 で枠を作らない。** 枠は**本編のスクリーン（`ScreenAnchor`）そのもの**。開口の大きさと
不透明度だけを動かす。だから段 6 に「枠を運ぶ」処理が無く、「入ったのに前方にスクリーンが浮いている」
矛盾も最初から発生しない。枠は現れるだけで、既にそこにある。

**段 5 のクロスフェードは 1.5 秒以上、体験者は静止したまま。** 映像の 100〜200ms 遅延と視差が同時に
来る唯一の不快点なので、歩きながら通過させない。

**段 5 の乱れは企画書 2.3 の手法をここで使う**（「差し替えの継ぎ目の隠蔽」）。導入で一度見せておくと、
本編で乱れが出たときに「またあれか」と読める。乱れの語彙を導入で教える。

## 5. 開始カメラ

**導入を開始した時点で体験者が居るゾーンの担当カメラ**を使い、**本編へもそのまま入る**（切替 0 回）。

- 通常は区間 1 = カメラ A。ただし体験者が段 0〜4 の間に移動していたら追従する
- カメラ A 固定にすると、動いていた場合に「A に入ったのに B の映像が点く」で矛盾が即座に露呈する
- 切替を 0 回に保つのは、**身分の変更（現実 → 映像）を体験中 1 回だけにする**ため。
  段 5 の直後に dip 付きの切替が入ると、せっかくの一撃が薄まる

⚠ 段 5 の自己認識は**正面性ではなく動きの随伴性**（手を上げる → 画面の中も上がる）で担保する。
だからカメラ A の側面ビューで足りる。正面のカメラ C を選び直す必要はない。

## 6. 技術（何が使えて、何が使えないか）

実パッケージ **`com.meta.xr.sdk.core@201.0.0`** のソースで確認済み。
⚠ `.claude/rules/meta-xr.md` の記述は古い（「v68 以降」「部分透過は surface-projected」）。本節に合わせて直す。

### 使えるもの

| やること | API | 確認したこと |
|---|---|---|
| パススルーを連続的に薄くする | `OVRPassthroughLayer.textureOpacity` | setter は `styleDirty` を立てるだけで、LateUpdate で 1 回だけ反映。**レイヤ再生成なし**＝毎フレーム変えてよい |
| 色を抜く / コントラストを上げる | `SetBrightnessContrastSaturation` | 実行時に連続変化可 |
| 監視カメラの色へ寄せる | `SetColorLut(source, target, weight)` | **2 枚の LUT を補間する口が最初からある**。weight 1 本で駆動できる |
| 実物の輪郭を光らせる | `edgeRenderingEnabled` / `edgeColor` | 動的 on/off・色変更可。**段 3 の「メッシュだけの世界」はこれで作る** |
| 枠（周縁を塞ぐ） | **Passthrough Windows** 方式 | 画面の alpha を書き、alpha 0 の領域だけパススルーを透かす。`float4(0,0,0,alpha)` / `Blend Zero SrcAlpha` / queue 5000 |

### 使えないもの / 制約

- **パススルーを on/off で切ると数百 ms の黒が出る**（公式に "black flicker"）。
  → 導入中は**切らない**。`textureOpacity` と style で見せ、本編に入ってから切る（そこは黒でよい）
- **走査線・粒状感・低解像度化・色収差はパススルーに掛けられない**（OS コンポジタが合成するため）。
  → アプリ側の全画面の面を重ねて出す。**加算とアルファは通る / 引き算と彩度操作は通らない**
- **深度が効かない**。パススルー面と VR オブジェクトの前後関係は深度で解決されない。
  重ね順は `compositionDepth` と Overlay/Underlay で設計する
- **`textureOpacity` の意味が `overlayType` 依存**。Underlay のまま 0 にしても「黒へ」ではなく「暗くなる」だけ。
  枠の外を黒にするのは Passthrough Windows 側（alpha を書く面）の仕事にする
- **surface-projected passthrough は 201.0.0 で `[Obsolete]`**。使わない
- **ガーディアン表示は消せない**（`SetVisible` 非推奨）。視点を動かさない設計なのでここは問題にならない
- `projectionSurfaceType` は**インスタンス化直後しか変えられない**。実行時に変えるならレイヤの disable→enable が要る

### 実装の形

| 何を | どこに | 流儀 |
|---|---|---|
| 段の進行（状態機械） | **新規 `IntroDirector`**（`Assets/Scripts/Streaming/`） | 判断は純ロジック `IntroLogic`（dt 注入・EditMode テスト）。`ShowRunLogic` と同じ分け方 |
| **`ShowPhase` は増やさない** | — | Intro の**内側のサブ状態**として `IntroDirector` が持つ。ゲート・終了判定・heartbeat・卓・シミュレータへの分岐を増やさない。`ShowRunLogic` への追加は「導入の計時を今から始める」1 メソッドだけ |
| パススルーの制御 | **新規 `PassthroughStyler`**（`Assets/Scripts/OvrBridge/`） | OVR に触るので asmdef なしの Assembly-CSharp 側（`OvrHandTrackingBridge` と同じ流儀）。`IntroDirector` からは値（0〜1）を渡すだけ |
| 枠（alpha を書く面） | **新規シェーダ + 面**（`CenterEyeAnchor` 配下） | `StartupFader` と同型の head-lock。生成は `MainDemoSceneSetup` の既存削除セクションと同じ流儀 |
| 粒・走査線・乱れ（全画面） | 同じ面のシェーダに載せる | `ScreenComposite` の post FX の式を流用する（**同じ見えにする**） |
| 構造の線 | 既存資産を使う | 位置合わせの検証ワイヤー（`CourseRegistrationController` が床外周と L 字壁を LineRenderer で描く）と `layout.room`。カメラの印は `cameras[].calib`／`pose` から |
| 人形が 1 回腕を上げる | カット側の指示を新設 | `steps[]` に「人形の合図」を足す。`ActorArmLogic` は idle 合流しか持たない |

## 7. データ契約（show.json）

トップレベル `run` の中に `intro` を足す。**キーが無くてもコード既定で成立する**（既存の show.json が壊れない）。

```jsonc
"run": {
  "totalLaps": 3, "introEnabled": true, "introMinSec": 20, "introAutoAdvance": true,
  "intro": {
    "enabled": true,            // false なら従来どおり（最初からスクリーンだけ）
    "maxSec": 40,               // 超えたら段を飛ばして枠を出す（保険）
    "realSec": 4,               // 段 1 現実
    "degradeSec": 8,            // 段 2 格下げ
    "structureSec": 6,          // 段 3 構造（段 2 と重なる）
    "frameSec": 5,              // 段 4 枠
    "swapSec": 8,               // 段 5 すり替え（クロスフェードは最低 1.5s）
    "edgeColor": "#ffffff",     // 輪郭線の色
    "showCameraMarks": true,    // 段 3 のカメラの印
    "showRoomWire": true,       // 段 3 の壁・床の線
    "glitchOnSwap": 0.8,        // 段 5 の乱れの強さ
    "raiseHandPrompt": true     // 段 5 の「右手を上げる」の合図を出すか
  }
}
```

- サーバ側は `capture-server.py` の `_STATE_KEYS`（`run` に含まれるので追加不要）と `_default_show()` の `run` に
  既定値を足すだけ
- Unity 側は `ShowRunDef` に入れ子で足す。**`ShowPhase` は増やさない**
- 卓は ⚙ 欄の run の隣に「導入」パネル（段ごとの秒 + on/off）。**本番前チェックに 1 行**足す
  （導入が有効なのに部屋が未実測 / 開始カメラが未較正 なら ⚠）

## 8. 成立に必要な条件（外すと壊れる）

1. **導入の立ち位置で、体験者の全身がカメラに写る。** 立ち位置は区間 1 の入口（企画書の縛り）で動かせないので、
   **カメラ A の三脚位置をこの制約で決める**。設営時に卓のライブ映像で「頭から足まで入る／HMD を被った人物だと
   分かる大きさ」を確認する。ここを外すと §2 の伏線ごと核心が消える
2. **段 5 の間、スタッフはそのカメラの画角外に退く。** 画面内に 2 人居ると「どれが自分か」が壊れる
3. **部屋の実寸が入っている。** 段 3 は現実に線を直接重ねるので、位置合わせの残差がそのまま目に触れる。
   `layout.wall` が既定の 1m×1m のままなら段 3 は成立しない（較正 UI の床寸法入力で直せる）
4. **「右手を上げる」は導入と 3 周目の 2 回だけに使う。** 壁をたどる右手とは**別動作**として分ける。
   多用すると合図としての意味が薄れる
5. **導入 → 本編の遷移で (lap 1, 開始カメラ) の区間進入を必ず 1 回通す。**
   [[show_run_skeleton]] に、ゲート適用順を誤ってスタート区間の 1 周目録画が黙って落ちた実害が記録されている。
   導入が長くなるこの設計は同じ穴を踏みやすい
6. **段 3 のワイヤーは位置合わせの現地検証点として使う。** 線が実物に重ならなければスタッフはそこで中止して
   再登録できる。これが段 3 を入れる理由の半分

## 9. 失敗モードとフェイルソフト

| 起きること | どうするか |
|---|---|
| カメラのフレームが来ていない | 段 5 へ進まず段 4 で待つ（枠の中はパススルーのまま）。`maxSec` に達したら**枠だけ出して本編へ**。砂嵐を見せない |
| カメラが全滅 | 続行ではなく**導入のやり直し**。技術で救えないのでスタッフに委ねる（卓に出す） |
| 体験者が横や後ろを向いている | 段 4 の開始を保留する（頭の角速度と向きを見る）。枠は**開始時点の頭 yaw** に出す |
| HMD を被り直された | 段 1 からやり直し。導入は**巻き戻せる相**にする |
| recenter が立った（トラッキング原点が変わった） | 導入を中止して黒 + スタッフ呼び出し。続行すると壁の位置が違う世界を見せる（体験者は壁を手でたどる） |
| 体験者が段 5 で手を上げない | 待たずに進む。上げなかった場合は伏線が張られないだけで、体験は壊れない |
| パススルーの style API が実機で効かない | 段 2 をアプリ側の面だけで作る（暗くなり粒が乗る。色は抜けない）。**段 2 自体は残る** |
| スタッフが介入したい | 卓から任意の段へ飛べる・全スキップできる。既存の `advanceIntro` と同じ世代カウンタ 1 つで足りる |

## 10. 検証

- **純ロジック**: `IntroLogic` の段遷移を EditMode テストで固定（尺・保留条件・`maxSec` の打ち切り・
  巻き戻し・カメラ不在時の分岐）

**設計から変えた点**（実装して分かったこと）:

1. **枠は head-lock にした**（設計は「開始時点の頭 yaw に出す」＝ワールド固定と書いていた）。
   ワールド固定にすると、頭を振ったときに覆いの外が見えてしまう。段 4・段 5 は体験者が静止している
   前提（段 4 の開始条件で頭の角速度を見ている）なので、head-lock で困らない
2. **`frameCentered` の意味を変えた**。枠が head-lock なら「枠が視野中心にあるか」は常に真で無意味。
   見るべきは「**本編のスクリーンの側が正面に来ているか**」（スクリーンは yaw を緩く追従する）
3. **`textureOpacity` は触らない**。Underlay では「暗くする」意味しか持たないので、枠の外を黒にするのは
   `IntroVeil`（alpha を書く面）の仕事に一本化した。役割を混ぜると、どちらが効いているのか分からなくなる
4. **パススルーは演出が終わってから切る**。切ると数百 ms の黒が出るが、その時点で覆いが黒いので
   体験者には見えない。本編は黒背景なのでパススルーを回し続ける理由が無い（90Hz を守る）
5. **`ShowIntroDef.LooksUnset` を足した**。JsonUtility はキーが無いと「全部 0 / false」の実体を作るので、
   それを検出して既定へ落とす。これが無いと `enabled=false` に化けて**演出が黙って出なくなる**
   （焼き込み・端末キャッシュに古い show.json が残っている場合に踏む）
6. **枠の開口は本編のスクリーンから逆算する**（`IntroVeil.ResolveAperture`）。同じ見かけ角にしておくと、
   枠が閉じ切った瞬間の枠と本編のスクリーンが同じ大きさになる
