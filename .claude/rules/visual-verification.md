# 視覚検証の作法 — 誤判定で working を壊さない

**発端（2026-07-01・実害）**: 手バリアントの Robot（機械リグ・多数の分割メッシュ）を **1〜2 角度のスクショだけで「指が崩れてる」と誤判定**し、
実際には正常動作していた式A実装を「ワールド空間 FK リターゲット」に大改修 → **working だった Realistic を逆に爪状へ退行**させた。
その後ユーザーの「角度が悪いだけでは」で**上面・単体隔離**を撮ったら Robot は普通のロボットハンドだった。式Aへ全撤去して復帰。

## 鉄則

1. **「壊れてる」判定は多角度で確認してから**。嵩張る/密集した/半透明/機械的な 3D は 1 角度だと重なって崩れて見える。
   最低でも **上面・正面・側面・単体隔離**を撮る。特に**上面**と**背景を排した単体**は誤解を切りやすい。
2. **正解基準と並べて比較する**。今回なら Default(Meta 白手=正解) と同フレームで並べれば一目で整合が分かった。
   「対象単体を眺めて壊れてる気がする」で判断しない。
3. **大改修の前に必ず現状を疑う**。「直す」前に *本当に壊れているのか* を上記で確定する。
   working な実装を、未確定の不具合を追って書き換えない（退行リスク > 得られる改善）。
4. **働いているものは触る前に退避**。式を差し替える等の破壊的変更は、元がコミット済み（＝`git checkout HEAD` で即戻せる）
   であることを確認してから。戻せないなら先にコミット/スタッシュ。
5. **撮り直しは安い**。角度・背景・単体隔離を変えて撮り直すコストは、誤判定に基づく数百行の改修より桁違いに安い。
   迷ったら「もう一角度」。

## 6. 実機の見た目は実機の画で確かめる（2026-07-31 追加）

Editor プレビューも数値検証も「実機で本当にそう見えるか」は答えない。**パススルー・シェーダの同梱・
XR の初期化は Editor では全部成立していて、実機でだけ死ぬ。** 実測: テレメトリが FAIL ゼロ・
演出 7 本 OK と判定した走行の画を録ったら、**導入演出が 1 段も出ていなかった**
（パススルー未初期化 / シェーダのビルド剥がれ / カメラ背景が不透明 の 3 件が同時に起きていた）。

→ **見た目に関わる変更をしたら [quest-capture](../skills/quest-capture/SKILL.md) で画を録る。**
HMD を被らずに撮れるので、実機確認をユーザーの手作業に頼らずに回せる。

## 7. 画を見るときは「縮小しない・密に切る・1 回で終わらせない」（2026-07-31 追加）

§6 の直後、**同じ日に別の原因でもう 1 回**「画に出ていない」を踏んだ。1 回目（パススルー 3 件）を
直した走行で、2 回目（`renderQueue` が URP の範囲外で構造の線と指示テキストが 1 度も描画されない）が
そのまま残っていた。見つけるまでに次の 3 つを踏んでいる:

- **縮小したら消えた。** 動画を一覧グリッドに落として見たら線が「0 本」に見えた。
  実際は 1cm 幅の線が 2m 先にあり、**縮小で 1〜2 画素になって潰れていた**。
  → **判定はフル解像度でする。**一覧グリッドは「どこを見るか」を決めるためだけに使う
- **段が短い。** 構造の線が出るはずの段は実測 **1.1 秒**しかなく、数秒刻みでは素通りする。
  → **段の長さをログで確かめてから、その中を 0.2 秒刻みで切る**
- **1 回直して録って終わりにした。** 1 回目の修正後の録画にも 2 回目の不具合は写っていたのに、
  「導入が出るようになった」で満足して細部を見なかった

→ 手順は [`tools/xp-evidence.py`](../../tools/xp-evidence.py) が機械化してある（ログの
`ev=intro stage=` の時刻を録画時刻へ写し、各段をフル解像度で切り出す）。
`quest-record.py` が走行後に自動で呼ぶので、**まず `index.md` の一覧を見て、
気になる段はフル解像度の PNG を開く**。

**ログに警告が出ていないことは「出ている」の証拠にならない。** 今回の 2 件はどちらも
マテリアル解決も配置処理も成功していて、コードは「出した」と思っていた。
`[XP]` の `veil=` / `wire=` / `pt=` / `bg=` はこれを機械で捕まえるために足したもの。

## 8. 「撮れていない」と「出ていない」を混同しない（2026-08-01 追加）

§6・§7 は「画を見ろ」と言っているが、**その画が撮れているかを先に確かめろ**が抜けていた。

2026-08-01 の実害: 導入演出の録画が全段まっ黒だったので「パススルーが合成されていない」と結論し、
Quest 再起動・URP の MSAA 変更と 40 分かけて追った。真相は 2 つの重なりで、どちらも不具合ではない。

1. **`screencap` はパススルーを拾わない**（`screenrecord` は拾う）。撮れない道具の出力を
   「出ていない」と読んでいた。詳細は [quest-capture](../skills/quest-capture/SKILL.md)
2. **部屋の照明が消えていた**。パススルーは平均 3/255 しかなく、画面がほぼ全面その暗さだと
   H.264 が丸ごと 0 へ潰す。持ち上げれば普通に映っている

- **撮れないものを撮れる形に置き換える**。現実の見えが撮れない状況でも、アプリが alpha を
  どう書いたかは撮れる — 背景を明るくすれば「覆いが開けた穴」が黒い矩形として写り、
  基準線を重ねればずれが画素で測れる
  （[`VeilAlignmentProbe`](../../Assets/Scripts/Diagnostics/VeilAlignmentProbe.cs)）
- **人にしか判定できないもの**（立体視のスケール感・酔い・質感）と
  **道具を作れば測れるもの**（幾何のずれ・追従の残差）を毎回分けて考える。
  今回は後者を前者だと諦めかけた
- **「〜が壊れている」と結論する前に、観測系の健全性を 1 つ確かめる。**
  今回なら「同じ場面を別の撮り方でも撮る」で 2 分だった

## 10. 「直った」ではなく「何に見えるか」で判定する（2026-08-04 追加）

CG 人形の髪を作り、**繋ぎ目が消えたことを確認して完了と報告した。実際には髪に見えていなかった**
（側面は角の丸い茶色い箱で、前後の境界線も残っていた）。ユーザーに指摘されて初めて気づいた。
§7 が「縮小するな」と書いた 3 日後に、同じことを別の形で踏んでいる。判断の欠陥は 6 つ:

1. **縮小した並置画像で品質を判定した。** 最後の判断に使ったのは頭を横 3 つ並べた画像で、
   1 つ幅 300px。フル解像度（1000px）で撮ったら一目で壊れていた。§7 の再発
2. **差分で判断し、絶対で判断しなかった。** 「前より良くなったか」だけを見て、
   依頼を「繋ぎ目を消す」「頭頂を丸くする」の 2 項目に還元し、上位の目的に戻らなかった
3. **実物と並べなかった。** 写真があるのに最後の判定で使っていない（§1 の違反）
4. **工数を理由に打ち切った。** 「時間が長い」「これで確定させる」と繰り返した
   （work-style.md §6 は時間コストを判断材料にするなと明記している）
5. **手段が成立したことを目的の達成と取り違えた。** 「前後で同じノイズにすれば繋ぎ目は
   原理的に消える」は正しいが、そのせいで前後が同じ縞になり**かえって不自然**になった。
   理屈の正しさは絵の正しさではない
6. **生成物そのものを見ていない。** 手続き生成したテクスチャを一度も拡大していない

→ **見た目の成果物を「完了」と報告する前に、次の 4 つを必ず通す:**

- **フル解像度で、対象だけを画面いっぱいに撮って見る**（一覧・並置は場所を決めるためだけ）
- **実物・正解基準と並べる**（差分ではなく絶対で見る）
- **「これは何に見えるか」を言語化する。** 「繋ぎ目が消えたか」ではなく「髪に見えるか」。
  言語化できない状態で「良くなった」と言わない
- **中間生成物（テクスチャ・マスク・法線）自体を開いて見る。** 生成コードが意図どおり
  走ったことは、出力が意図どおりであることを意味しない

「もう時間をかけた」は判定を緩める理由にならない。壊れているものを完了と報告する方が高くつく。

## 9. 片眼で合っていても両眼では合っていない（2026-08-01 追加）

VR の画は左右の眼で別々に描かれる。**片眼だけ切り出して測ると、両眼視差に由来するずれが
原理的に見えない。**

実例: 導入の枠は片眼の実測で「四辺とも 0.29 度以内」と判定できていたのに、ユーザーが録画を見て
「枠の外に何かはみ出している」と気づいた。左右の眼を並べて数えたら
**左眼は右側だけ・右眼は左側だけ**に漏れていた（33,616px / 27,948px、逆側はどちらも 600px 未満）。
左右で逆＝視差以外にありえない。原因は、穴を描く面が眼から 0.3m・対象のスクリーンが 2m にあり、
**穴を中央眼から解いていた**こと。近い面に描いた穴は、左右それぞれの眼から見ると別の方向にずれる。

- **重ねるものと重ねられるものは、同じ距離に置く。** 面を対象と同じ距離へ運べば、
  穴の縁のワールド位置が対象の縁と一致し、どちらの眼から見ても合う
- **左右を並べて比べるのを、視覚検証の定型に入れる。** 片眼の数値がいくら良くても、
  左右で符号が反転する成分は片眼では絶対に出ない
- **立体に関わる最終判定は被る。** 録画から詰められるのはここまで（この日それで 2 回外した）
