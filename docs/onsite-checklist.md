## 0. 当日の素材撮り — 白衣と接近クリップ（設営後 10 分・2 人）

準備画面は `tools/web-compositor/serve.ps1 -Prepare` で起動する。
「設営 → 接続 → 撮影 → 演出 → ビルド → 開場前」の順に進む。
撮る前に対象スマホの担当と映像を確認する。Quest と博士タブレットの最終確認はビルド後でもよい。
スマホで撮影したテイクは、PC の同じ画面の「撮影」で回収する。採用中の素材は「演出」で APK 内の素材と並べて見られる。

**`canon/LEDGER.md` 0102 / 0104。2 周目 B・2 周目 C の差し込みはここで撮った人形視点だけで走る。**
撮らなければそのカットは実機が飛ばして、C はただのライブへ退化する（体験は続くが接近は無い）。

> ⚠ **照明を本番と同じにしてから撮る。** 人形視点が同じ部屋の映像に見えるかは照明の一致がすべて。
> 撮り直しは安いが、照明が違う素材は何度撮っても使えない。

> ⚠⚠ **撮る前に配信スマホの充電ケーブルを抜いて冷ます。**
> 熱段が 0 でない端末で撮った素材は本番と粗さが揃わない
> （撮影コンソールの本番前チェック「接近の素材」④ が warn で名指しする）。
> **配信を止めるだけでは足りない** — 2026-08-23 の実測で、encode を完全に止めても
> 充電したままの端末は 8 分で 43.8 → 43.3℃ しか下がらず、熱段 4 のままだった
> （同じ時間で充電中でも負荷の軽い端末は 3 → 2 へ落ちた）。

> ⭐ **手順はスマホの「🎬 撮影」が 1 ショットずつ誘導する**（v0.13.0〜）。
> 撮る人が持っている端末に、指示文・**画に出るのは頭 N 秒**・⏺・撮れたテイクの尺・
> 「卓へ送って採用」までが並ぶ。**卓まで歩かなくてよい。**
> 卓の準備画面の「撮影」（`http://localhost:8099/#shoot`）は、選び直しと
> **頭の窓の試写**（大きな画面が要る仕事）のために残っている。
> 下の 0.2 は「何をどう撮るか」の中身で、**順番と尺はスマホと卓が同じ所（`shots.json` ＋ 台本）から出す**。
>
> ⚠⚠ **配信アプリは v0.14.0 以上**（撮影パネル・補助線・鏡合わせ・構えている最中の窓）。
> v0.10.0〜0.12.0 なら卓からの遠隔操作だけで撮れる。v0.9.0 以前は
> コンソールが端末に **「旧アプリ（要 v0.10.0）」**と赤で出し、1 本も撮れない。
> **v0.15.0 で画面の作りが変わった** — 押す所は**横持ちなら右の列**（映像には重ならない）。
> カメラ ID とレンズは**左のカメラ ID を押す / 🔭 を押す**とダイアログで選ぶ
> （下の列は無くなった。本番中の誤タップでスロットが入れ替わる事故を潰したため）。
>
> ⚠ **B の端末を POV に借りるなら、B を取り付ける前に撮る**。
> 取り付けた後に外して戻すと較正が壊れ、開場直前に位置合わせをやり直すことになる。

### 0.1 白衣を着せる

- [ ] スタンドイン（撮影される人）に白衣を着せる
- [ ] **体験者にも被せる前に着せる**（HMD の上から羽織らせない・前掛け型なら HMD と干渉しない）
- [ ] 渡すときは「調査員の制服です」で通す（機材の都合に見せない）

**なぜ**: 監視カメラの粗い画で人物の同定に使えるのは**服の色と形だけ**。そこを揃えると
「白衣が映っている ＝ 自分が映っている」と読まれる。副産物として、服装の個人差が消えて
誰が来ても録画素材が成立し、暗い部屋で白衣は明るいので背景差分（入れ替わりの芯）も立ちやすくなる。

> ⚠⚠ **偽ライブ（カメラ C の当日録画）は 2026-08-22 に廃止した**（`canon/LEDGER.md` 0104）。
> 差し込むのは**人形視点だけ**で、2-C の連続演出中はライブへ戻らない
> （戻るのは追いつきの直後・体験者が黒マスクに覆われるとき）。人形視点の動画は下の 5 本。その後で A・B・C の無人静止画も撮る。

### 0.2 人形視点（`pov_0` / `pov_1` 〜 `pov_4`）

手持ちスマホ。**高さ 40cm 固定**（人形の目線）。毎カット必ず C の立ち位置へ**正対**する
（横に逸れると「部屋の紹介」になる）。

⚠⚠ **使われるのは各素材の頭だけ**（下の「画に出る所」）。**録画ボタンを押した直後から本番** —
構え直す時間は画に出る。いちばん見せたい状態から撮り始めて、少し長めに回して止める。

| cue | 撮り方 | 画に出る所 | 撮る長さ |
|---|---|---|---|
| `pov_1` | 遠い。白衣は米粒 か 不在 | 頭 **1.0 秒** | 3 秒 |
| `pov_2` | 近い。歩きの揺れが出る速さで | 頭 **0.9 秒** | 3 秒 |
| `pov_3` | すぐそこ。白衣の一部が画面に入る | 頭 **0.8 秒** | 3 秒 |
| `pov_4` | **白衣の背中の至近（0.5m）**。<b>寄り切った所から</b>撮り始める | 頭 **1.4 秒** | 3 秒 |
| `pov_0` | 2 周目 C の頭で 1 度割り込む。**部屋の隅からの遠景・人物なし** | 頭 **0.9 秒** | 2 秒 |

⚠ `pov_4` は「ゆっくり寄って最後だけ速く」ではない — **頭 1.4 秒しか出ない**ので、
寄る過程を入れると追いついた瞬間が画に出ない。**もう届いている所**から撮る。

### 0.2b 反映する

**道は 2 つある。どちらでも同じ所へ着く。**

| 誰が | どうする | 使う場面 |
|---|---|---|
| **撮った人** | 端末の「🎬 撮影」→ 撮れたものの行 →「卓へ送って採用」 | その場で尺を確かめたい（**既定**） |
| **シュビー** | 「撮った」と言われたら `py -3.11 tools/onsite.py takes --adopt` | 押し忘れた・卓が居なかった・後から撮り直した |

`takes` は**端末に残っているものを卓から取りに行く**。各 cue の**いちばん新しいテイク**を
回収 → 検分 → 採用まで済ませ、要求秒に足りないものは赤で名指しする。
古いテイクは端末に残す（戻したくなったときの唯一の道）。反映したら **APK を焼き直す**
（`.\tools\unity.ps1 build fixedcam`。show.json は毎回焼き込まれる）。

**撮った端末の「🎬 撮影」でそのまま終わる場合:**

- [ ] ショットを選ぶ（**上の横並びの札**）→ 指示文と **画に出るのは頭 N 秒** を読む
- [ ] **⏺ 撮る** — 構えて 3・2・1（1 秒ごとに振動）→ 指定の尺で自動停止
- [ ] 撮っている最中に **「画に出る 1.4 秒まで あと 0.9 秒」** が出る。足りるまで止めない
- [ ] 撮れたものの行で **「卓へ送って採用」**。卓が測った実測が返る
      （`3.1 秒 / h264 / 640x480`、足りなければ **⚠ 尺が足りない — 撮り直す**）
- [ ] 一覧の印が **✅** になれば、そのショットは済み

⚠ **卓に繋がっていなくても撮れる。** ファイルは端末に残るので、卓が立ってから送ればよい
（画面上部に「卓が見つからない」と出る）。

### 0.2c 卓で見直す（頭の窓の試写だけ）

**スマホから回収した素材は、卓の準備画面（`http://localhost:8099/#shoot`）に
そのまま並ぶ。** ここでやることは 1 つだけ — **画に出る所を大きな画面で見る**。

- [ ] **② 画に出る所だけ見る** — 実機で出る頭の窓だけがループする。ここで良し悪しを決める
- [ ] 頭がぶれていたら **「頭を送る」**に秒を入れて **この頭で採用**（元のテイクは残る）
- [ ] **採用**を押すと cue に入る（同じ cue を指すカットが複数あれば全部に効く）
- [ ] 5 本すべてに ✅ が付いたら **✅ 本番前チェック**へ（「接近の素材」と「演出素材」が緑）
- [ ] **▶ 検証**で 2 周目 C を通し、飛び飛びの間合いと追いつきの後の黒を目で見る
- [ ] 人形視点の採用が終わったら §0.3 へ進む。最終ビルドは必要な合成素材も確定してから行う

**外から持ち込んだ動画を使うとき**（コンソールを使わない退避路）:
`tools/web-compositor/recordings/` へ置き（**mp4 で**。webm なら
`py -3.11 tools/web-compositor/to-mp4.py <ファイル>`）、🎬 タイムラインのカット詳細
→ **cue を編集** → **合成素材** → 💾 保存。

⚠ **参加者が映っている時間を最小にする**（0102）。映るほど「動きが自分と違う」に気づく機会が増える。
だから遠い所から始めて、白衣が画面に入るのは最後の 2 カットだけにする。

### 0.2d カメラ A を左右対称に据える

**3 周目 A は画面の左半分を右半分の鏡像として読む**（`canon/LEDGER.md` 0050）。
A は L 字経路の手前で唯一環境が左右対称なので、**その対称軸を画の横中央に合わせて据える**。
ずれたぶんだけ、体験者の鏡像と本物の立ち位置が食い違う。

- [ ] A の端末で **🪞 鏡で確かめる** を押す（左半分が右半分の鏡像に置き換わる）
- [ ] **継ぎ目（縦の中央線）が消える**ように三脚を振る・寄せる。上部の
      「左右のずれ N（小さいほど対称）」が下がる向きへ動かす
- [ ] **傾き**が緑（±1° 以内）になるまで水平を出す。傾いていると鏡の軸が部屋の対称面と揃わない
- [ ] 決まったら 🪞 を切る（見たままの画へ戻す）

⚠ **鏡合わせをするのは A だけ。** B・C は環境が左右対称ではないので、対称に据えると
かえって不自然になる（端末も B・C では鏡の軸を既定で出さない）。

### 0.3 人形視点の後に A・B・C の無人シーンを撮る

- [ ] 人形視点の 5 本を撮り終える。借りたスマホを本番の固定位置へ戻す
- [ ] A の左右合わせを済ませる。本番の照明に固定する
- [ ] 撮影者とスタンドインも画面の外へ出る
- [ ] 準備画面の「撮影」→「各カメラの無人シーンを撮る」で A・B・C を 1 枚ずつ撮る
- [ ] 各写真を見て無人であることと構図・照明を確認する。チェックを入れて採用する
- [ ] A を採用すると `plate_A` と `plate_A_right` が同じ写真へ更新される。B と C は各 `plate_B` / `plate_C` へ反映される

撮影だけでは現在の採用を変えない。元の素材も残る。カメラや照明を動かした場合は撮り直す。
この撮影経路で当日撮影して採用した 3 枚がそろうまで、ビルドの依頼文はコピーできない。

### 0.3b 会場の写真を元に必要な演出を作る

上で採用した A・B・C の無人静止画を使う。人形視点の 5 本は撮った動画をそのまま使う。
合成用の画像や動画は、会場の写真と合わない演出だけ作り直す。まず写真から画像を作り、動きが必要なものはその画像から動画にする。
事前素材を使う演出まで一律に再生成しない。手形の当日への合わせ方は [gen-plate の手順](../tools/gen-plate/README.md) を参照する。

- [ ] 素材工房で配信映像に重ね、位置と明るさを確認してから採用する
- [ ] 人形視点の冒頭を撮影コンソールで試写し、当日撮影・採用が 5 本そろったことを確認する
- [ ] 「演出」で現在の採用素材と APK 内を見比べる。「仮採用・要ビルド」は次の APK へ反映する素材。APK の素材一致と実機への導入は別の確認
- [ ] 当日の会場で撮ったことと採用素材の試写を人が確認する。回収時刻を撮影時刻として扱わない
- [ ] 素材を確定してからビルド用に書き出す。APK を焼いて Quest α と β の両方へ入れる

### 0.4 凍結の線と録画の起点（3 周目 A）

- [ ] 卓の **📏 通過ライン**で `line_freeze` を**通路の狭い所へ短く**引き直す
      （現行は「検証用の仮置き」。歩線の違いがずれになるので短い方がよい）
- [ ] その行の **🪞** を押す → `line_rec_start` が画像空間の鏡へ焼き直される
- [ ] **✅ 本番前チェックの「🪞 鏡の線」が緑**になることを確認

⚠⚠ **`line_freeze` と `line_rec_start` は対の資産。片方を動かしたら必ず 🪞 を押す。**
course 空間で対称に置いても、カメラ A が対称軸の真上に無い限り**画面上では対称に写らない** ＝
「録画が凍結位置の外から始まる」。押し忘れは本番前チェックが ❌ で名指しする。

## 2. 現場に着いてから（起動と確認）

**当日ユーザーは PC を触らない。** 押す物はスマホの当日パネル
`http://192.168.10.10:8099/onsite.html`（同じ LAN なら誰の端末からでも開く）。
判断が要ることはシュビーに頼む（`.claude/skills/onsite/SKILL.md`）。
博士タブレットはホーム画面の「廻リ視 博士」を開く。起動時はスタッフ画面になる。
クエストα／βを本体のラベルと照合して選び、接続を確認する。
画面と博士の説明素材はタブレット内にある。設定は選択したQuestへ直接送る。
設営と毎回の交代は [博士タブレットの設営](../tools/visitor-ui/README.md) と
[スタッフ起動・交代フロー](../.claude/memory/staff_setup.md) を参照する。
充電と横向きと博士の声を確認する。

0. [ ] **ルータ（Aterm）を先に立てる。** 2.4GHz・5GHz のランプが両方点くまで待ってから端末を繋ぐ
   - 手順の正本は [onsite/network-setup.md](onsite/network-setup.md)。**IP は端末側で静的に振ってある**ので、
     ここで IP をメモして書き換える作業は**もう無い**（`.21`=A / `.22`=B / `.23`=C / `.24`=D / `.10`=PC）
1. [ ] **PC を起こす（ログオンする）。** 卓はログオン時に自動で立つ
   （スタートアップの `mawarimi-desk`）。
   ⚠ **サインイン画面で止まっていると立たない** — 自動ログオンは切ってあるので、誰かが 1 度サインインする
2. [ ] スマホ全台で配信アプリを起動し、画面の **cameraId が割当と合っているか**見る
3. [ ] **配信スマホを USB に挿して、無線 adb を開ける**

   ```bash
   py -3.11 tools/onsite.py adb-open
   ```

   ⚠⚠ **端末を再起動すると閉じる。** 閉じていると、当日その端末が落ちたとき**遠隔で 1 手も打てない**
   （画面を起こすのもアプリを起こし直すのも adb 経由）。設営のたびにやる
4. [ ] **点検を 1 回通す。** Quest を本番と同じ台数だけ起動してから

   ```bash
   py -3.11 tools/onsite.py check --deep
   ```

   NG が 0 になるまで開場しない。行ごとに直し方が出る。スマホからなら当日パネルの「点検する」
5. [ ] **設営と照明が決まったら、3 台とも端末の 🔓 露出/AF ロックを押す**
   （素材を撮った時と本番で色が変わるのを止める。点検が warn で名指しする）
6. [ ] **会期中は監視を走らせておく**

   ```bash
   py -3.11 tools/onsite.py watch
   ```

   20 秒ごとに全カメラから実際にバイトを引き、出ていなければ起こし直す。卓が落ちていれば立て直す

> ⚠ Unity の設定とコードの変更は前日までに終える。当日は撮影・生成した素材を確定してから最終 APK を焼く。
> 両 Quest へ入れ直した後は、設定の反映と実機の映像・音をもう一度確認する。

### 2.1 最初の準備

- [ ] Questで「廻リ視」を起動する。タブレットで同じ本体のα／βを選ぶ。
- [ ] スタッフがQuestを装着し、右トリガーを2秒押して位置合わせを始める。カメラの接続待ちでも始められる。
- [ ] 右手の近くに今の点と操作と測定値が出る。床の×印と先端を見ながらAを押したまま0.5秒静止する。右手が見失われたら前へ出す。
- [ ] 実物とガイド線を目視してBで確定する。保存済みの位置も目視してから再利用する。
- [ ] 位置合わせ中に頭の向きの基準が変わった場合は、点1から採り直す。Aを一度離してから記録する。
- [ ] タブレットで機器6項目の確認件数とスマホA・B・Cの状態を確認する。不調の行に出る案内に従って配信を直す。
- [ ] タブレット本体の音量を確認する。0または消音なら本体ボタンで上げる。
- [ ] 「困ったとき」の「通知音を確認する」を押し、端末から短い音が聞こえることを確認する。

ヘッドセットの更新が止まったと表示されたら、電源ボタンを1回押して復帰させる。
台に置くときの自動スリープはQuestのOS設定による。会場では「設定 > 電源 > 自動スリープ」を確認し、設営と説明の間に止まらない長さを人が選ぶ。
アプリはOS設定を変更しない。

### 2.2 体験者ごとの交代

1. タブレットが「体験が終わりました」になるまで待つ。「終わりの演出中です」の間はリセットしない。
2. HMDとヘッドフォンと左コントローラーを回収する。清拭と充電を確認する。
3. 回収画面の次の準備ボタンを1.5秒押し続ける。「次の体験者の準備ができました」を確認してから「来場者の画面にする」を押す。
4. 来場者へタブレットを渡す。言語と恐怖軽減を選んでもらい、博士の説明を進める。
5. 「スタッフへ返す」の後にタブレットを受け取る。設定の実値と機器の状態を確認し、「長押しで装着へ進む」を1.2秒押し続ける。
6. Questの確定応答の後に博士の装着案内が自動で進む。タブレットを置いて両手で装着を補助する。左コントローラーの練習と本編開始は来場者がQuest内の指示に従って行う。

装着へ進む確認の後に開始を妨げる異常が6秒続くと、タブレットが短い音で一度知らせる。画面の機器名と直し方を確認する。異常が続く間は繰り返し鳴らない。回復後の新しい異常は再び知らせる。体験の開始後と終わりの演出中と終了後は鳴らない。タブレットが背景にある間の異常音を後から再生しない。

途中で中止が必要なときは、スタッフが持つ右コントローラーのAを2秒押し続ける。
タブレットには本編中の中止ボタンを置かない。

## 5. 切り分けフローチャート（接続問題 vs ロジック問題）

```
HMD を被る
  │
  ├─ Quest にアプリすら起動しない / 一覧に出ない
  │   → APK ビルド・インストール失敗
  │     ・adb devices で Quest が `device` として見えるか
  │     ・Build Settings に Main.unity が enabled で入ってるか
  │     ・Player Settings: ARM64 / IL2CPP / API 29+
  │     ・Build And Run のログを Console で確認
  │
  ├─ 起動した・映像出るが FPS < 60
  │   → パフォーマンス問題（実装側）
  │     ・OVR Metrics Tool で GPU / CPU を切り分け
  │     ・Profiler 接続（USB or Wi-Fi、AndroidPlayer 選択）
  │     ・Phase 3 FX を OFF にして再測（原因 FX を二分探索）
  │     ・MjpegScreen.Update の GC Alloc を Profiler で確認
  │
  ├─ 起動した・スクリーンが真っ黒
  │   → 接続問題 or 描画設定問題
  │     [接続疑い]
  │     ・PC から配信 URL がブラウザで見える？
  │     ・Quest と PC とスマホが同一 LAN（5GHz）？
  │     ・CameraSource の host/port/path 正しい？
  │     ・スマホがモバイル回線にフォールバックしてないか？
  │     [描画疑い]
  │     ・Quad の Material が URP Unlit か（Lit だと暗転）
  │     ・Quad の表裏（裏面消失）
  │     ・Color Space: Linear
  │     ・Auto Graphics API: OFF / Vulkan が最上位
  │
  ├─ 押しても振動もしない・何も反応しない
  │   → コントローラ未接続を最優先で疑う
  │     ・操作ガイドパネル（右コントローラ追従）が消えている？ → コントローラ未接続（電池 / スリープ / ペアリング落ち）
  │     ・振動はするが機能しない → 入力は届いている（下の入力ブリッジ問題へ）
  │
  ├─ 映像出る・手動切替が効かない
  │   → 入力ブリッジ問題
  │     ・押下で振動する？ 振動する＝入力は届いている → registry / director 側を疑う
  │     ・OVRCameraRig 配下に OVRManager がいるか（OVRInput 初期化に必要）
  │     ・OvrControllerBridge の registry / screenAnchor 参照がアサインされているか
  │     ・asmdef を持たない場所（Assembly-CSharp）に OvrControllerBridge が居るか
  │       （asmdef 配下から OVRInput を直接呼ぶと参照解決が必要）
  │     ・キーボード Tab で切替できる？ できれば Registry は生きている → ブリッジ側の問題確定
  │
  ├─ 切替効く・ゾーンで自動切替しない
  │   → 物理空間 or PlayerZone 設定
  │     ・PlayerZone.halfExtents が現場サイズに合ってない（広すぎ / 狭すぎ）
  │     ・PlayerZone.centerOffset が床基準で設定されているか（HMD 高さ ≈1.6m を考慮）
  │     ・PlayerZoneTracker.zones にシーンの全 PlayerZone が刺さっているか
  │     ・Scene ビュー / Editor の Gizmo（緑半透明 Box）でゾーン位置を再確認
  │
  └─ ゾーン切替効く・FX が出ない
      → URP RendererFeature 配線
        ・Settings/URP の UniversalRendererData に FullScreenPassRendererFeature が入ってるか
        ・FX 用 Material（FxCrtMaterial 等）がアサイン済みか
        ・カメラの Renderer Index と Renderer 設定が一致しているか
        ・Tools > FixedCamVr > Setup > Create CRT Material を実行済みか
```

## 6. シュビーが Console から状態を読む（HudLogDumper / HmdTrajectoryRecorder）

HMD 装着者しか見えない値を、PC 側 Console / MCP からも読めるよう
`HudLogDumper`（[`Assets/Scripts/Diagnostics/HudLogDumper.cs`](../Assets/Scripts/Diagnostics/HudLogDumper.cs)）が `Diagnostics` コンテナに自動アタッチされる。

- 出力タイミング: **状態変化（CONN / CAM index / ZONE label）時に 1 行 + 30 秒に 1 回定期 ping**
- フォーマット例: `[HudDump #12 t=45.6 why=zone] FPS=72.3 CONN=1 CAM=2/3 Phone02 ZONE=Right@0 HMD=+2.31,+1.62,+0.04`
- シュビーが取る方法: MCP `read_console filter_text="HudDump" count=100` で時系列が抽出可能

ログが流れて埋もれない設計なので、ユーザーは特に意識しなくてよい。

### 6.1 ゾーン形状の調査用: `HmdTrajectoryRecorder`

「歩いてもカメラが切り替わらない」等、**ゾーン形状を実測ベースで詰めたい時のみ**有効化する一時計測コンポーネント。
[`Assets/Scripts/Diagnostics/HmdTrajectoryRecorder.cs`](../Assets/Scripts/Diagnostics/HmdTrajectoryRecorder.cs)。

- Setup Main Demo Scene を実行すると `Diagnostics` コンテナに **自動でアタッチされる**（常時 ON 想定ではないので、調査が終わったら GameObject から Component を削除して良い）。
- 出力: 1 Hz で `[HmdTrace #N t=X.X] pos=(x,y,z) zone=Label cam=N conn=0|1 Center=in/inShrunk Right=in/inShrunk Left=in/inShrunk`
  - `in` = AABB に含まれるか（0/1）
  - `inShrunk` = `hysteresisShrink=0.15m` を効かせた縮小 AABB に含まれるか（0/1）
  - 両方 0 の区間が出れば、それがデッドゾーン（どのゾーンにも属さず Tracker が `keepLastWhenOutside` で前ゾーンに張り付いている領域）
- 抽出: `read_console filter_text="HmdTrace" count=200`
- **Quest Link 経由で Editor Play 中に動かす**前提。スタンドアロン APK で起動した場合は `adb logcat -s Unity *:I | findstr HmdTrace` で取る。

## 7. 不具合発生時の記録テンプレ

その場で潰せない不具合は次セッションに引き継ぐため、以下を記録：

```
- 発生時刻:
- フローチャートのどの分岐で詰まったか:
- 直前の操作（カメラ番号 / ゾーン / FX 状態）:
- HMD 内で見えていた状態（スクリーン色 / 文言 / 振る舞い）:
- Editor Console のエラー（コピペ）:
- adb logcat 抜粋（adb logcat -s Unity *:E）:
- 暫定回避策（FX OFF / カメラ固定 / スマホ再起動 等）:
- 再現性（毎回 / 散発 / 1 回のみ）:
```

> ログ取り: `adb logcat -s Unity *:E > onsite_YYYYMMDD_HHMM.log` を別ターミナルで流しっぱなしにしておくと、後追いが楽。
