接近シーンの当日撮影 — 設計

2 周目 B・C「偽ライブ ⇄ 人形視点」の素材 6 本を、当日焦らずミスらず撮って反映する環境 ／ 2026-08-22 ／ 設計のみ・実装は未着手

P0（8 カットの連続再生が実機で成立するか）は測り終えた — 成立する。 8 カットすべてが著作どおりの間隔で走り、画も毎カット切り替わっていた。停滞（発火してから画に出るまで）は素材の先読みを実装して 最大 280ms → 166ms（最短カット 0.5 秒の 56% → 33%）。素材は mp4 のままでよい。
残る柱は 3 本。①録画を配信アプリの端末内録画へ一本化（streamer v0.10.0）、②卓に撮影コンソール（1 ショットずつ誘導 → 自動回収 → 頭だけ試写 → 採用）、③検査を本番前チェックへ機械化。

2. P0 — 測った: 8 カットの連続再生は実機で成立する 実測済み

設計検討で最初に立った指摘は「この演出の再生自体がまだ実機を通っていない」。testassets の動画を 6 つの cue へ仮当てして走らせ、計装（ev=clip）を足して測った。

結果

落とす用意（Prepare）合計最短カット 0.5s の
先読みなし0〜152ms128〜167ms最大 280ms56%
先読みあり（実装済み）0ms（9/9 キャッシュ）120〜166ms最大 166ms33%
  • 8 カットすべて played=1。間隔は 1.21 / 0.71 / 1.00 / 0.71 / 0.81 / 0.61 / 0.51 / 1.20 秒で著作値と一致
  • 画も毎カット切り替わっていた（録画から切り出して確認）。偽ライブの trim も設計どおり進み、C の再生位置が 0.5 → 2.0 → 2.3 → 3.6 → 3.9 秒と動いていた
  • 残る停滞は Prepare の 135ms 前後。_player.Stop() → url 代入 → Prepare() を毎カット通るためで、同じファイルでも短絡しない。消すには VideoPlayer を 2 本持って次カットを先行 Prepare するしかない（未実装・実機で人が見て要否を判断する）

実装したもの（この判断のために入れた）

何どこ
停滞の計装（ev=clip id= dl= prep= tot= cache=）ScreenOverlayController.ClipLatency → ShowTelemetryHost → analyze-xp-log.py「## 動画カットの停滞」
動画素材の先読みScreenOverlayController.PrefetchVideo ← ShowControlClient.PrefetchTimelineClips（無人プレートの先読みと同じ立ち位置）

ev=step played=1 は「画面を取った」しか言わないので、停滞は ev=clip にしか出ない。本番素材は数 MB なので、先読みが無ければ落とす時間はテスト素材（24KB）よりさらに伸びていた。逆に、先読みが効いていれば素材の大きさは停滞に効かない。

参考: 判断の分かれ道だったもの（いずれも不要になった）

  • クリップのカットは毎回 _player.Stop() → URL 代入 → Prepare() を通る。同じファイルでも短絡しない（ScreenOverlayController.cs:283-295）
  • カットの尺は発火時刻から数える（TakeRunnerLogic.cs:692）。Prepare 中は前のフレームが凍結表示されるので、Prepare が 0.3 秒なら 0.5 秒のカットは 0.2 秒しか画に出ない
  • 動画は発火時に初回ダウンロードする（ScreenOverlayController.cs:288）。事前に読むのは無人プレートの静止画だけ（ShowControlClient.cs:2263 付近）。つまり最初の偽ライブのカット（1.2 秒）の中で DL と Prepare の両方が走る
  • 8/22 の実機走行（logs/evidence/20260822_*）は cue の sourceUrl が空 ＝ クリップのカットは全部飛ばされ、保持（swapHold）とプレートだけが検証された

測り方（コード変更ほぼゼロ）

  1. testassets/ の 6 秒動画（fake_live の要求 5.5 秒を満たす）を 6 つの cue へ既存の cue エディタで仮当てする
  2. py -3.11 tools/quest-record.py --sec 60 --walk を 1 回（両機に APK を入れてから・--serial 指定）
  3. 各カットが画に出た実秒と、DL / Prepare の停滞を測る。テレメトリに無ければ ShowTelemetryHost と analyze-xp-log.py を対で足す（既存規約の範囲）

結果による分岐

方式判定
mp4 ＋ 先読み採用。停滞 166ms（最短カットの 33%）。素材の形式は mp4 のままでよく、撮影環境の設計はそのまま成立する
2 本目の VideoPlayer で次カットを先行 Prepare保留。残り 135ms を消せるが実装が重い。実機で人が見て要否を決める（数値だけで判断しない）

8 カットを 1 本に焼く不要。ショット単位の採用・撮り直しが崩れる最後の手だった

3. 録画は端末内録画へ一本化する

streamer には既に端末内録画がある（FrameRecorder.kt: 配信と同じ JPEG フレーム列を MediaCodec で H.264 mp4 に焼く。全フレーム I フレーム・実タイムスタンプ・容量 / 30 分ガード付き。/record/start ほか 4 endpoint も実装済みで、現在未使用）。これを主経路にする。

観点ブラウザ ⏺（現行）端末内録画（採用）
画の一致MJPEG を canvas 経由で再エンコード（1 世代劣化 ＋ ブラウザのタイマー任せ）配信とまったく同じフレーム。偽ライブが本物に見える根拠が定義上成立
Wi-Fi 断テイクが欠けるテイクは端末内で完走。回収は復帰後でよい
形式webm(VP9) → ffmpeg 変換必須（ffmpeg 不在で詰む）H.264 / yuv420p の mp4 が直接出る。変換工程ごと消える
頭の切り出しGOP 依存でシークが粗い全 I フレームなので -ss … -c copy で再エンコードなしに正確
構図の確認撮り手からは見えない撮り手が端末画面で見ながら構えられる（決め手はここ）

偽ライブは設置済みカメラ C の端末へ卓からリモート開始（端末に触らない ＝ 構図を乱さない）。POV は手持ちの streamer 端末。ブラウザ ⏺ は fallback として残す。

5. 卓の撮影コンソール（shoot.html）

別ページにする（sim.html と同じ立て付け）。ライブ卓の 1 ページを太らせず、当日はこの画面だけを全画面で使う。判定は shoot-model.js（DOM 非依存の純関数）＋ node テスト — 卓の流儀のまま。

ショットの定義はコードに置く（show.json に足さない）

  • cue にフィールドを足す案は却下。cue エディタは保存時にフィールドの白名簿でオブジェクトを作り直す（cue-editor.js:225-231）ので、未知キーは次に誰かが cue を保存した瞬間に消える（serializeStep で実害の出た型と同じ）
  • ショット 6 個（cueId・表示名・指示 1 行・撮る長さ・撮る手段）は shoot-model.js の定数。要求尺（頭の窓）だけは timeline から機械導出する — fake_live なら参照カットの max(trimStartSec + durSec) = 5.5 秒。著作が変われば要求も追従し、手順書が古びない

テイクの流れ（1 ショット 1 画面）

  1. ショットカード — 指示 1 行（「白衣の背中の至近。もう届いている所から」）・対象端末のライブプレビュー（/cam プロキシ）・傾き表示（/caminfo の実測値）・端末の熱と容量（/record/status）
  2. ⏺ — 偽ライブは卓からリモート開始（maxSec=10・カウントダウンなし）。POV は撮り手が端末のボタンで開始（カウントダウン 3 秒）
  3. 自動停止 — 規定秒で止まる。手で ⏹ を数える仕事が消える
  4. 自動回収 — 卓が /record/list の差分で新テイクを検知 → 取得 → 検分（実尺・解像度・向き・熱段）→ 台帳へ登録。テイクの帰属はコンソールでいま選ばれているショット（取り違えは次の試写で見える）
  5. 頭ループ試写 — 実際に画面へ出る頭の窓だけをループ再生。「使われるのは頭だけ」を UI の形そのもので言う
  6. 採用 / 撮り直し — 採用で cue の sourceUrl が入る。テイクは全部残り、前のテイクへワンクリックで戻せる

採用まわりの決め（3 つとも事故の防波堤）

決め理由
頭合わせはファイル側を切る（採用時に in-point を指定 → -c copy で頭切りした別ファイルを採用。元テイクは残す）。step の trimStartSec は触らない撮影都合の値を著作へ書くと、素材を差し替えたとき古い頭合わせが別素材に効く。偽ライブの 0 / 1.9 / 3.6 / 5.0 は「頭からの進み」の設計値として意味を保つ
採用はサーバ側の 1 API（POST /shoot/adopt が show.json のメモリを直接更新・rev++）。shoot.html から /state を丸ごと POST しない/state は cues 配列ごと差し替えるので、開きっぱなしの卓の他画面の編集を消す
採用ファイル名は毎回一意（テイク番号＋時刻）Quest は URL → ローカル DL のキャッシュを持つ（ScreenOverlayController.cs:73）。同名で差し替えると撮り直したのに古い版が再生され続ける

台帳は recordings/approach-manifest.json（サーバが書く）: ファイル・ショット・テイク番号・回収時刻（卓の時計が正。端末の時計は名前のヒント扱い）・端末 id・撮影時の熱段・検分結果・採用フラグ。最後に既存の ▶ 検証（L2C1#0 / L2C2#0 の通し試写）と ✅ 本番前チェックへの 1 クリック導線を置く。

6. 検査 — ✅ 本番前チェックに「接近の素材」行

効く順に並べる。①②が赤なら体験が壊れ、③④が赤なら偽ライブがばれる。

#検査何を防ぐか
①採用漏れ・ファイル欠損・実尺不足（要求＋0.5 秒未満）カットが実機で飛ばされ、C がただのライブへ退化する
②録画しっぱなしの端末（発見済み全端末の /record/status）本番中ずっと熱と容量を食い、配信の品質が落ちる
③採用素材の撮影日が今日でない前会場の素材の混入 ＝ 照明不一致。何度検分しても直らない最悪の事故
④撮影時と現在の熱段の不一致（S2 で撮った素材は q25 / 15fps — ライブが S0 だと粗さが合わない）偽ライブとライブの質感が食い違い、切り替えの瞬間にばれる
⑤解像度・向きがカメラ C と同一（640×480 横）letterbox の形が変わって「別の映像」に見える
保留偽ライブの頭と現在のライブの明るさ差④が先に同じ事故を捕まえる。④で不足と分かったら足す

7. 当日の回し方（2 人 10 分のまま・順序で再取付リスクを消す)

POV 撮影用の 4 台目が無い現場では B の端末を借りるが、較正済みの端末を外して戻すと較正が壊れる。撮る順序で回避する:

  1. 照明を本番と同じにする（ここから先の素材だけが有効）
  2. 白衣を着せる（§0.1 のまま）
  3. B を取り付ける前に、その端末を手持ちにして POV 5 本を撮る（コンソールが 1 本ずつ誘導・撮り手は端末画面で構図を確認）
  4. B を取り付けて較正する（外して戻す、が発生しない）
  5. C の端末へ卓からリモートで偽ライブを録る（C には誰も触らない）
  6. コンソールで採用 → ▶ 検証で通し → ✅ 本番前チェックが緑

予備の 4 台目があればそれを使う（cameraId「?」のままで発見される）。手順書 docs/onsite-checklist.md §0 の書き換えは実装と同じコミットで行う（doc-sync）。

8. 堅牢性 — 障害と挙動

障害挙動
録画中に Wi-Fi 断テイクは端末内で完走。回収は復帰後に /record/list の差分で拾い直す
卓サーバ / PC が落ちる録画は端末単体で成立。台帳は回収時に端末側の一覧から再構築できる
ffmpeg 不在端末経路は変換不要なので撮影は完走。頭切りだけ不可 → 「頭切りなしで採用」へ縮退し警告
端末の容量・熱既存ガード（1GB / 500MB / 30 分・熱スロットル）＋ ショットカードに常時表示
撮り直したのに変わらない一意ファイル名で構造的に起きない（§5）
show.json の巻き戻り書き込みは全部サーバ API 経由。ファイル直書きはしない（既知の罠のまま）
本番中に誤って ⏺コンソールは Unity heartbeat のラン進行を見て録画開始を止める（警告バー）

10. やらないこと

  • /record/plan と端末側ショットリスト UI — 状態の二重化。カウントダウンと自動停止だけで「押してから構える」は直る
  • 継ぎ目カード（trim 境界の前後フレームを静止画で並べる面）— 「0.7 秒ぶん人が動いたか」は静止画 2 枚では判定できない。▶ 検証の通しで見る
  • 頭ループ試写への本番画質トグル — ▶ 検証と重複
  • 明るさ差の検査 — 熱段の検査（§6 ④）が先に効く。保留
  • 目の視界ジャック（当日写真）の統合 — 台帳の形は将来載せられるようにしておくが、範囲外
  • Unity のこれ以上の変更 — 先読みまでで停滞は 33% に収まった。残り 135ms（Prepare）を消す二重 VideoPlayer は、実機で人が見て必要と判断したときだけ

著作判断として残るのは 1 つ: POV を監視カメラと同じ粗さで出すか（端末内録画に一本化すると自動でそちらへ倒れる）。canon/OPEN.md に案として置いた。既定は「同じ粗さ」で、コンソールは外部ファイルの取り込み口を残すのでいつでも覆せる。

検討の経緯: 設計案を design-critic（独立レビュー）に通し、verdict 部分採用。指摘で変えた点 — 実測 P0 を先頭へ／cue へのメタ追加を却下（保存白名簿で消える）／一人撮影フローと継ぎ目カードを削除／検査の優先順を入れ替え。コードの指摘は全件 grep で実物照合済み。
