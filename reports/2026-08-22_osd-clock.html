スクリーンの時刻表示（OSD）

canon/LEDGER.md 0108 ／ 実装済み（2026-08-22）・実機未検証 ／ 契約の正本は rules/streaming.md

スクリーンの左上に 2026/09/06 14:23:45 の形で日付と時刻を常時出す。 描くのは ScreenComposite シェーダの 1 層（砂嵐の後・管の縁の前）で、 虚構上はカメラではなく観測装置（画面の側）が打っている時計とする。 だからカメラ切替・差し込み・録画・砂嵐のどれでも表示は変わらず、 3 周目の録画の上にも「いまの時刻」が進み続ける — 録画には焼き込まれていないので、これが構造的に成立する。 時刻は端末の実時刻（既定）。場所表示と報告数は出さない（ユーザー判定）。

2026-08-22 に実装した。 EditMode 1620/1620・menu osd の 8 状態で 「映像側の異変（砂嵐・乱れ・劣化）では変わらず、装置側（切替の黒・終幕の電力）では一緒に沈み、 まだ何も映していない管には出ない」ことを確認。実機未検証 — 1 字 1.0° が被って読めるかは 机上で決められない。

1. 何を出すか

項目値理由
文字列2026/09/06 14:23:45（19 字・すべて半角） 参考画像 004.jpg と同じ yyyy/MM/dd HH:mm:ss。秒が刻むこと自体が「ライブである」の主張
場所映像の左上（枠ではなく contain-fit の内側）。余白は枠の高さの 4% 参考画像どおり。管の角丸（_CrtRound 0.07）に掛からない位置。
⚠ 枠の左上に置くと字が letterbox の黒帯に乗る — 映像は 4:3・枠は 16:9 なので 左右に必ず黒帯が出て、そこだけコントラストが最大になり主張が強くなる（実装中に絵で見て直した）
大きさ1 字の高さ ＝ 枠の高さの 2.43% ＝ 見かけ 0.89°。 文字列の全幅は枠幅の 18.3% 参考画像 004.jpg の実測に合わせた（画像 512×288 で字高 7px = 2.43% / 全幅 95px = 18.6%）。 HmdTextStyle の段（補助 1.5°）より小さいのは意図 — これは読ませる面ではなく画の一部。 ⚠ 実機で 2 回続けて「読めない」を出した前歴があるので、走行で必ず確かめる（§7）
字体・詰め等幅セル。セル幅 ＝ フォントの送り幅（送り/字高 = 0.71） 監視カメラの OSD の姿。等幅でないと秒の刻みで幅が揺れる。
⚠ 同梱フォントの数字は幅/字高 = 0.706 で、参考画像（0.71）とほぼ同じ比率だった — ずれていたのはセル幅だけで、初版は 40px 取っていて参考より 64% 広く字が離れていた （2026-08-22 ユーザー赤入れ「文字の詰め方等は参考画像に合わせてほしい」）
色生成り (232,226,214) ＋ 不透明な暗い縁 5px（版に焼き込む） 参考画像は白＋影。純白だと暖色の画の上で 1 か所だけ浮く。
⚠ 縁が読みやすさの主役 — 実測で縁 3px では砂嵐（平均輝度 140）の上のコントラストが 9.9 しか無く読めなかった。5px・不透明で 19.3（素の状態も 36.1 → 42.5）
出さないもの場所（CAM2 廊下 相当）・報告数ユーザー判定（0108）。区間が短く 3 つしかない／決められた数が無い

2. 時刻の出どころ

既定は端末の実時刻（DateTime.Now）。当日が 9/6 なら自動で 2026/09/06 になり、リハーサルの日はその日の日付が出る — どちらも現実なので嘘がない。 「装置は正直に映している」がこの作品の恐怖の土台（rules/sound-design.md §1）で、 時計だけは絶対に嘘をつかないことが「スクリーン＝現実」の担保になる。

  • 固定の日付（例: 本番前でも常に 2026/09/06）にしたい場合は世界観の判定なので canon/OPEN.md の問 Q12 に既定つきで置いた。返事が無ければ実時刻で進む
  • 実時刻を使う以上、Quest 2 台の時計のずれが体験者に見える。 実装時に docs/onsite-checklist.md §0 へ「2 台の時計を確認」を 1 行足す

3. どの層で描くか（設計の核）

TMP の面ではなく ScreenComposite シェーダの 1 層として合成する。 面を別に立てると _ScreenPower（終幕の電池切れ）・dip・管の曲面・縁の暗さに乗らず、 「画面の上に別の層が貼ってある」＝合成の証拠そのものになる。 StaffViewing の門・ZTest の罠（TitleNotice が 1 文字も出なかった件）とも無縁になる。

挿入点は砂嵐（_SignalLost の混合）の後・管の縁（_CrtEdge）の前:

ソース（mip 劣化・夜間モード）→ CG 人形 → レンズ → センサ → ISP(post)
  → 走査線 → aura → 乱れ → 入れ替わりの覆い → 管の点灯 → 砂嵐
  → ★ OSD（時刻）
  → 管の縁・角丸 → dip（切替の黒） → _ScreenPower（終幕）

この位置の意味: 映像（feed）に起きることは OSD に及ばず、 装置（画面）に起きることは OSD も一緒に受ける。 虚構として「時計はカメラではなく観測装置が打っている」（DVR の OSD と同じ）で一貫する。

場面表示なぜ
導入 段 0〜3（空の管）出ない（× _IntroLive）装置は点いているが、まだ何も映していない
導入 段 4〜5（映像が出る）映像と一緒に現れる覆いのセル越しに映像ごと見え始める
カメラ切替（dip）黒には一緒に沈み、明けても同じ時計が続くdip は装置側。時計は連続
人形視点の差し込み・3 周目の録画・無人プレート出続ける。時刻は「いま」のまま進む§4 — この設計の核心
乱れ（_Glitch）乱れない（後段なので）乱れは伝送側。映像だけが裂けて時計は微動もしない ＝「表示は現実」が立つ
信号断（砂嵐）砂嵐の上に出続けるfeed が切れても装置は時刻を知っている
周回の劣化・夜間モード影響を受けない（鮮明なまま）劣化は伝送・撮像側。粗い映像の上の鮮明な OSD は実物の DVR と同じ
左右分割・凍結・持続の覆いその上に乗る合成後の最上段なので個別対応が要らない
終幕 Flicker画と一緒にちかちか消える（_ScreenPower）電池が切れるのは画の一部ではなく装置そのもの（0048）
目の視界ジャック・位置合わせ特別扱いなし（視界ごと乗っ取られる／スクリーンごと扱われる）—

4. 録画との関係 — なぜ「合成でない感じ」が構造的に立つか

  • 端末内録画（SegmentRecorder）は配信の生 JPEG 列で、OSD は焼き込まれない。 3 周目にその録画が流れるとき、上に乗る OSD はいまの時刻で進み続ける — 装置が「これは今の映像だ」と主張し続けるので、映像の中に自分が居ないという反転が 「録画だから」で説明できなくなる
  • 人形視点の mp4・無人プレート・生成画像も同じ。どのカットにも同じ時計が乗る ＝ すべて「同じ装置がいま映しているもの」に見える
  • 逆に、OSD を録画側へ焼き込む方式（画面録り）にすると 3 周目に過去の時刻が出て種明かしになる。だから表示時合成の一択

実装中に絵で見つけた罠

  • 版の v を反転してはいけない。 Unity はテクスチャを左下原点で持つので、 PNG の 1 行目（字の上）は v=1 側。矩形の上端も o.y=1 なのでそのまま渡す。 1.0 - o.y にすると字が上下逆さまに出た（1 回書いて menu osd で発見）
  • 矩形の内外を分岐にしない（step のマスクで切る）。 非一様分岐の中でテクスチャを引くと暗黙の微分＝ミップの段の選択が壊れる
  • 敷き直し先はミップを持たせる。実機では 1 字が約 16 画素まで縮むので、 無いと秒が刻むたびに字がちらつく

6. 観測（音と同じく、出たかはログでしか分からない要素がある）

  • ev=sum に osd=<組めたか>/<刻んだ回数>/<不透明度> を足す。 「組めたか」＝材質を掴めてテクスチャを書けたか（効果の実在）、 「刻んだ回数」＝秒の縁で敷き直した累計（時計が進んでいる証拠）
  • 判定は analyze-xp-log.py の「## 効果の実在」節へ: 本編で組めていない → FAIL ／ 電源が入っているのに刻みが止まっている → FAIL。 ShowTelemetryHost と対で直す（片方だけだと沈黙して食い違う）
  • 画の証拠: quest-record.py --walk → xp-evidence の PNG 左上に写る。 縮小一覧では 1.0° の字は潰れるので、判定はフル解像度で開く（visual-verification §7）

7. 見る手段と検証

  • menu osd（Play 不要）: 固定時刻（2026/09/06 14:23:45）で 8 状態を PNG に焼く — 素 / 砂嵐 / 乱れ最大 / 劣化最大（3 周目相当） / 切替の黒 / 終幕の電力 / 導入 段 4 / 導入 段 0〜3。 固定時刻なのは決定論のため（同じ版は同じ絵。プレビューに実時刻を混ぜない）。 ⚠ 実装（ScreenOsd）をそのまま通す（矩形の式も敷き直しも模写しない）
  • 字が出ているかは数値でも測れる: 素の絵から「字の画素」のマスクを作り、 各状態でマスク内外の輝度差を見る。実測 — 素 67.3 / 砂嵐 50.0 / 乱れ 64.6 / 劣化 62.0 / 切替の黒 45.9 / 終幕 43.5 / 導入段 4 41.9 / 導入段 0〜3 は 1.2（＝出ていない・期待どおり）。 ⚠ 最大輝度だけで見ると背景が明るい状態（砂嵐・夜間モード）で判定できない
  • EditMode: OsdClockLogicTests 10 本（書式・秒の縁・版との対応・ Python と C# のセルの並びの一致）
  • 実機走行: osd= キーと PNG。1.0°/字が実際に読めるかは被って確かめる （見かけ角の机上見積もりは 2 回続けて外した前歴がある — hmd_text_style.md）

8. やってはいけないこと

  • ❌ 録画へ焼き込まない。 3 周目に過去の時刻が出て種明かしになる（§4）
  • ❌ 時刻で嘘をつかない。 巻き戻し・停止・加速などの時計の演出は、 「装置は正直」という 3 周目の土台を壊す。やりたくなったらユーザー判定（canon）を先に取る
  • ❌ 文字化け（CommsGlitch）を移植しない。 呪いに侵されるのは AI の面。 装置の時計まで化けると「装置も嘘をつくかもしれない」になる。 装置が死ぬのは終幕の電力（_ScreenPower）だけ
  • ❌ TMP の面にしない（§3 の理由）
  • ❌ 場所・報告数の行を足さない（0108 のユーザー判定）
  • ❌ 全角にしない。時刻はデータそのもの（HmdTextStyle 書式 4・5 の側）
