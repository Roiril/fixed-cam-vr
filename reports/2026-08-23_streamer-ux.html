配信アプリに「据える」と「撮る」を置く

fixed-cam-streamer v0.13.0 ／ 2026-08-23 ／ 実装・JVM テスト 142 件・APK ビルドまで完了。実機で触ってはいない

置き場を役割で決め直した。 三脚に据える人も、人形視点を撮る人も、見ているのはスマホの画面であって卓ではない。それなのに据える補助は 1 つも無く、撮る操作は卓からの遠隔だけだった。
足したのは 2 つ。①補助線と鏡合わせ（カメラ A を左右対称に据えるための道具）、②撮影パネル（今日撮るもの・⏺・尺の確認・卓へ渡すが 1 画面）。卓の在り処は、卓が既に出しているブロードキャストから自動で入る。

1. いまの形

当日、配信スマホの前後で 3 人が別のことをしている。

誰何をする何を見ていたか（改修前）
据える人三脚に載せて A / B / C の位置と向きを決めるプレビューと傾きの数値だけ。構図の手掛かりは無い
撮る人人形視点 5 本を手持ちで撮るプレビューだけ。指示も、撮れたかの判定も、卓にしか無い
卓の人採用・検分・本番前チェック撮影コンソール（shoot.html）

これで何が起きるか。

  • カメラ A は左右対称に据えないと 3 周目 A の演出が崩れる（canon/LEDGER.md 0050 — A は L 字経路の手前で唯一環境が左右対称）。それを確かめる手段が現場に無かった。ROUNDS.md の実測でも「カメラ A は対称軸の真上に無い」と書いてある
  • 撮る操作が卓専用。撮る人は卓まで歩くか、卓の人に口で頼む。撮れた尺が足りているかも、卓の画面を見に行かないと分からない
  • 撮っている最中に「あと何秒必要か」を知る手段が無い。止めてから短かったと分かる

2. 決めた線引き

据える＝端末が正「A は左右対称」は台本の事実。卓が落ちていても据えられる必要がある。だから端末のコードに持ち、卓からは配らない
撮る＝卓が正・面は端末何を何秒撮るかはその日の台本で決まる。端末に写しを持たせると、台本を直した日に手元の指示だけが古くなる。指示は卓から配り、操作の面は端末に置く
卓に残すもの大きな画面が要る仕事だけ ——頭の窓の試写と選び直し。撮影コンソールはそこへ縮む

3. 据える — 補助線と鏡合わせ

鏡の軸は「配信画像の横中央」

3 周目 A は画面を縦に割り、左半分だけライブを左右反転して読む。反転は ScreenComposite.shader の uvSrc.x = 1.0 - uvSrc.x —— つまり枠 UV の 0.5 で、contain-fit は左右対称なのでソース画像の横中央が鏡の軸になる。

出るもの

補助線中身既定
鏡の軸配信画像の横中央に縦線cameraId が A のときだけ
水平縦中央に横線 ＋ 傾き ±1° 以内かで色が変わる（TiltMath の値）同上
三分割3×3手動
🪞 鏡で確かめる左半分を右半分の鏡像に置き換える ＋ ずれの数値手動

B・C で鏡の軸を既定にしないのは、合わせてはいけないから。あの 2 台は環境が左右対称ではないので、対称に据えるとかえって不自然になる。端末は cameraId ごとに一言添える（B・C は「左右反転はカメラ A だけ」）。

なぜ鏡合わせなのか

「左右対称に据わっているか」を目で測るのは難しい。壁の縁が数 cm ずれていても気づけない。そこで本番と同じことをその場でやる。左半分を右半分の鏡像に置き換えて出せば、判断が「対称かを測る」から「継ぎ目が見えるか」に変わる。

数値も添える。画像とその左右反転との平均絶対差（MirrorMath.symmetryError）で、小さいほど対称。⚠ 絶対値には意味が無い（照明と被写体で基準が動く）。使い方は「同じ場面で下がる向きへ動かす」だけで、閾値で合否は出さない。

踏んだ穴 — 鏡合わせは「需要」だった

鏡合わせは配信されている JPEG を横から読む。需要駆動 encode（DemandPolicy）が数えていたのは /video の接続と録画だけなので、誰も見ていない現場では encode が止まり、据えている最中に画が固まる。しかも症状は「カメラが壊れた」の顔で出る。

FrameDistributor.localPreview を足して需要の第 3 項にした。⚠ videoClients を増やして済ませない —— あれは /health の clientCount として卓に出るので、「誰かが見ている」と嘘をつくことになる。

4. 撮る — 撮影パネル（🎬）

順画面要点
①ショット一覧（✅ / ⚠ / —）採用状況は卓が持っているものをそのまま出す
②指示文と「画に出るのは頭 1.4 秒（2 カットで使う）」要求秒は台本の timeline から機械導出。著作を変えれば追従する
③⏺ 撮る（構えて 3・2・1 → 指定の尺で自動停止）既存の端末内録画（v0.10.0）をそのまま使う
④録画中に「画に出る 1.4 秒まで あと 0.9 秒」止めてから短かったと分かる形にしない
⑤撮れたもの（尺・送信済み・採用中・短い）端末の実測は再起動しても残る（SharedPreferences）
⑥「卓へ送って採用」卓が測った実測が返る。足りなければ ⚠ 尺が足りない（要求 1.4 秒 / 撮れた 1.0 秒）— 撮り直す

端末 → 卓の 2 本

口何
GET /shoot/plan?cam=<id>今日撮るもの。shots.json ＋ show.json の timeline から卓が導く
POST /shoot/collect撮ったテイクを卓へ。回収 → 検分 →（adopt なら）採用まで 1 往復
  • 端末は自分の IP を送らない。 卓は接続元アドレスから取りに来る。テザリングや複数 NIC では「端末が思っている自分の IP」と「卓から見えるアドレス」が食い違う
  • この口を足すために _shoot_pull / _shoot_adopt を中核（辞書を返す）とハンドラ（応答を書く）に割った。検分・一意名・台帳・頭送りの作法を 2 つに割らないため
  • 卓が居なくても撮れる。 ファイルは端末に残り、後から送れる（画面上部に「卓が見つからない」と出る）

5. 卓の在り処は、既にブロードキャストされていた

最初に考えたのは「卓 → 端末の HTTP リクエストに X-Desk-Url ヘッダを付ける」。やめた。それだと卓の画面を開いている間しか届かない（端末を叩くのは撮影コンソールのポーリングだから）。

卓は 5 秒ごとに fixedcam-discovery/1 の show-server announce を出している（capture-server.py の _disc_sender）。端末はそれを拾って送信元 IP ＋ httpPort を刻むだけでよい。プロトコルの変更も、現場での設定作業も、卓の画面を開いておく必要も無い。

⚠ ブロードキャストは誰でも出せるので、DeskAddress が形を検める —— IPv4 リテラル ＋ ポート、パスなし、http のみ。端末が卓へ送るのは撮った動画だけで、送るのは撮った本人が押したときだけ。

6. 単一の正が 1 つ動いた

ショットの定義（指示文・尺・構える秒）は shoot-model.js の定数だった。読む相手が 3 つになったので外へ出した —— ブラウザ・卓のサーバ（Python）・配信スマホ。JS の定数のままでは Python から読めず、スマホへ配る指示文が二重管理になる。

置き場読む相手
tools/web-compositor/shots.jsonshoot-model.js（loadShots()）／ capture-server.py（_shots_def()）／ 配信スマホ（/shoot/plan 経由）

移植を「気をつける」で守らない

「頭に何秒要るか」（neededHeadSec / cutCount）が JS と Python の 2 つになった。期待値を shoot-fixture.json に置き、node と Python の両方が同じファイルを食う。片方だけ直せば必ずどちらかが落ちる。

/shoot/plan が返す欄の名前も 2 言語にまたがる契約なので、PlanPayloadContractTest が欄の集合ごと固定した。黙って改名すると、スマホは既定値を読んで「全部 — のまま」「短いのに緑」になる。例外は出ない。

もう 1 つ、読み込む前の穴を塞いだ。SHOTS は空で始まり setShots() で入るので、読む前に判定を呼ぶと空配列 ＝「この台本は接近を使っていない」＝ 緑を返してしまう。shotsLoaded() の門を置いて ❌「shots.json が読めていない」を出す。

8. 確かめたこと・確かめていないこと

確かめた

  • JVM テスト 142 件（+28）と node 27 件（+3）・Python 35 件（+11）が緑。APK は assembleDebug が通る
  • GET /shoot/plan?cam=A を HTTP 経由で叩き、5 本すべてに要求秒が出た（0.9 / 1.0 / 0.9 / 0.8 / 1.4 秒 ＝ 手順書の値と一致）
  • POST /shoot/collect を端から端まで通した。配信端末もどきを立て、回収 → ffprobe の検分 → 台帳 → 要求との突き合わせまで。6 秒の素材で short=false、0.57 秒の素材で short=true
  • 不正な名前（../../secret.mp4）を弾くこと、届かない端末で理由が返ること

確かめていない

  • 実機に入れて触っていない。 鏡合わせの見え方（8fps・640×480 の復号が体感でどうか、継ぎ目の読み取りやすさ）、撮影パネルの文字サイズと押しやすさ、卓の自動発見が現場の Wi-Fi で何秒で入るか
  • ⚠ 卓サーバは再起動しないと新しい口を持たない。 いま動いているものは改修前のコードで立っている
  • ⚠ 配信スマホの APK 更新は USB が要る（無線 adb は無効）。入れた直後はアプリが止まっているので monkey で起こす
