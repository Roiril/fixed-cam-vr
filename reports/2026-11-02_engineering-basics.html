1. プログラムが動くまで

ソースコードと実行ファイル

人が書く文章がソースコードです。C# なら .cs ファイルに書きます。CPU はこれをそのまま読めません。

そこでコンパイラという道具が、ソースコードを CPU が実行できる形に変換します。この変換をコンパイルと呼びます。

コンパイラは変換のついでに、文法の誤りと型の誤り（2 章）を探します。見つかるとコンパイルが失敗し、実行ファイルは作られません。これをコンパイルエラーと呼びます。

実行中に起きる誤りは実行時エラーです。たとえば何も入っていない変数を使おうとしたときに起きます。コンパイルエラーは書いた直後に分かり、実行時エラーは動かすまで分かりません。だから、誤りをコンパイルエラーの側へ寄せる工夫が設計の大きなテーマになります。

廻リ視の場合

  1. Assets/Scripts の .cs を Unity がコンパイルする
  2. ビルドで Quest 用の実行ファイル Builds/mawarimi.apk を作る
  3. APK を Quest に入れて起動する

APK は Android アプリの配布形式です。Quest の OS は Android をもとにしているので、この形式を使います。

フレーム

ゲームや VR は、画面を 1 秒間に何十回も描き直します。1 回の描き直しをフレームと呼びます。Quest 3 は 1 秒に 90 回です。1 フレームに使える時間は約 11 ミリ秒です。

この時間を超えると描き直しが間に合わず、画面がカクつきます。VR ではこれが酔いにつながります。プロジェクトの規約に「90 FPS 維持」があるのはこのためです。FPS は Frames Per Second（1 秒あたりのフレーム数）です。

確認問題

Q1. コンパイルエラーと実行時エラーの違いは？

コンパイルエラーはコンパイルの段階で見つかり、実行ファイルが作られない。実行時エラーは動かしてみて初めて起きる。前者は書いた直後に気づけるので、後者より安く直せる。

Q2. Quest 3 で 1 フレームに使える時間はおよそ何ミリ秒？

1000 ÷ 90 ≒ 11 ミリ秒。

2. 値と型

プログラムが扱うデータを値と呼びます。すべての値には型があります。型は「その値がどんな種類のデータか」と「何ができるか」を決めます。

型中身例
int整数3（周の数）
float小数0.15f（メートル）。末尾の f は float の印
bool真か偽の 2 択true / false
string文字列"2026/09/06 14:23:45"
DateTime日時new DateTime(2026, 9, 6, 14, 23, 45)
Vector3x, y, z の 3 つの float頭の位置

型が誤りを止める

型が合わない使い方はコンパイルエラーになります。

int lap = "3";      // エラー：string を int に入れられない
int lap = 3;        // OK

ただし同じ型どうしの取り違えは止まりません。廻リ視には「進むだけの周」と「引き返すと戻る周」があり、どちらも int です。

void NotifyLap(int progressLap) { ... }

int segmentLap = 2;
NotifyLap(segmentLap);   // 意味が違う値を渡しているのに、コンパイルは通る

これを防ぐには、意味ごとに別の型を作ります（5 章・17 章の「値オブジェクト」）。

enum（列挙型）

決まった選択肢だけを取る値には enum を使います。廻リ視の体験の段階はこう書かれています。

// Assets/Scripts/Streaming/ShowRunLogic.cs
public enum ShowPhase
{
    Intro,     // 導入
    Run,       // 本編
    Finished,  // 終了
}

これを string で "intro" と書くこともできます。しかし "intoro" と打ち間違えてもコンパイラは気づきません。ShowPhase.Intoro ならコンパイルエラーになります。

null

null は「何も入っていない」を表す特別な値です。null の変数を使おうとすると実行時エラーになります。

型名の後ろの ? は「null が入るかもしれない」という印です。

// Assets/Scripts/Tracking/PlayerZoneTracker.cs
public PlayerZone? CurrentZone => _current;   // まだどのゾーンにも入っていなければ null

ファイルの先頭の #nullable enable を書くと、コンパイラが「null かもしれない値を確かめずに使っている」箇所を警告します。実行時エラーをコンパイルの段階へ寄せる工夫の 1 つです。

確認問題

Q1. 状態を string ではなく enum で持つ利点は？

選択肢以外の値を入れるとコンパイルエラーになる。打ち間違いを実行前に見つけられる。

Q2. float? x の ? は何を表す？

x に null が入りうること。

3. 変数と関数

変数

値に名前を付けて置いておく場所が変数です。

int totalLaps = 3;   // 型 名前 = 最初の値;
totalLaps = 4;       // 後から入れ替えられる

入れ替えられたくない値には const（コンパイル時に決まる定数）か readonly（最初に一度だけ決まる）を付けます。

関数（メソッド）

処理に名前を付けたものが関数です。C# ではクラスの中に書くのでメソッドと呼びます。

// Assets/Scripts/Streaming/OsdClockLogic.cs（読みやすく整えた）
public static string Format(DateTime t)
{
    return string.Format("{0:D4}/{1:D2}/{2:D2} {3:D2}:{4:D2}:{5:D2}",
                         t.Year, t.Month, t.Day, t.Hour, t.Minute, t.Second);
}
部分名前意味
string戻り値の型この関数が返す値の型。何も返さないなら void
Format関数名呼ぶときに使う名前
DateTime t引数呼ぶ側から受け取る値
return ...戻り値呼ぶ側へ返す値

呼ぶ側はこう書きます。

string s = OsdClockLogic.Format(DateTime.Now);

副作用と純粋関数

関数が戻り値を返す以外に外の世界を変えることを副作用と呼びます。画面に描く、ファイルに書く、変数を書き換える、音を鳴らす、などです。

副作用が無く、同じ引数なら必ず同じ戻り値を返す関数を純粋関数と呼びます。Format は純粋関数です。2026/9/6 14:23:45 を渡せば、何回呼んでも "2026/09/06 14:23:45" が返ります。

純粋関数は確かめやすく、壊れにくい関数です。11 章のテストで、この性質が効いてきます。

逆に DateTime.Now（今の時刻）を関数の中で読むと、呼ぶたびに結果が変わります。だから Format は時刻を中で読まず、引数で受け取っています。

確認問題

Q1. 次の関数は純粋関数か？ int Add(int a, int b) { return a + b; }

純粋関数。外の世界を変えず、同じ引数なら同じ結果を返す。

Q2. 次の関数は純粋関数か？ void Log(string s) { Debug.Log(s); }

純粋関数ではない。ログを書くという副作用がある。

Q3. Format が時刻を中で読まず引数で受け取るのはなぜ？

中で今の時刻を読むと、呼ぶたびに結果が変わって確かめられないから。引数にすれば、確かめる側が好きな時刻を渡せる。

4. 条件・繰り返し・状態

条件分岐

if (lap > totalLaps)
{
    // 周を走り切った
}
else
{
    // まだ途中
}

選択肢が多いときは switch を使います。

switch (phase)
{
    case ShowPhase.Intro:    ...; break;
    case ShowPhase.Run:      ...; break;
    case ShowPhase.Finished: ...; break;
}

繰り返し

for (int i = 0; i < zones.Length; i++)   // i を 0 から 1 ずつ増やし、zones の数だけ回す
{
    var z = zones[i];
}

foreach (var z in zones)                // 配列の要素を先頭から 1 つずつ取り出す
{
}

zones は配列です。同じ型の値を並べたもので、zones[0] が先頭です。番号（添字）は 0 から数えます。

状態と状態機械

プログラムが「今どういう状況か」を覚えている値を状態と呼びます。

状態がいくつかの段階を持ち、決まった条件で次の段階へ移る仕組みを状態機械（ステートマシン）と呼びます。段階の移り変わりを遷移と呼びます。

廻リ視の骨格は状態機械です。

Intro ──(導入が終わった かつ スタート区間に居る)──→ Run ──(周を走り切った 等)──→ Finished
  ↑                                                                              │
  └───────────────────────(次の体験者のためにリセット)───────────────────────────┘

これを持つのが ShowRunLogic です。毎フレーム Tick というメソッドが呼ばれ、条件を見て遷移するかを決めます。

// Assets/Scripts/Streaming/ShowRunLogic.cs:184（引数の一部）
public ShowRunEvent Tick(float dt, bool atStartZone, bool takeRunning, bool introCompleted = true, ...)

dt は前のフレームから経った秒数です（delta time の略）。状態機械は今の時刻を自分で読まず、経過時間を引数で受け取っています。3 章の純粋関数と同じ考え方です。

状態の持ち主は 1 つにするのが原則です。同じ状態を 2 か所で持つと、片方だけ更新されて食い違います。

確認問題

Q1. 配列 a に要素が 3 つあるとき、最後の要素は何と書く？

a[2]。添字は 0 から数える。

Q2. 状態の持ち主を 1 つにするのはなぜ？

2 か所で持つと、片方だけ更新されて値が食い違うから。

5. クラスとオブジェクト

クラス

クラスは、データ（フィールド）と処理（メソッド）をまとめた型の定義です。int や string と同じく型の 1 つで、自分で作れる点が違います。

public class Counter
{
    private int _count;            // フィールド：このクラスが持つデータ

    public void Add()              // メソッド：このクラスができること
    {
        _count = _count + 1;
    }

    public int Count => _count;    // プロパティ：外から読むための口
}

オブジェクト（インスタンス）

クラスは定義なので、それだけでは動きません。new でクラスから実体を作ります。この実体をオブジェクトまたはインスタンスと呼びます。

var a = new Counter();
var b = new Counter();
a.Add();
a.Add();
b.Add();
// a.Count は 2、b.Count は 1

同じクラスから作っても、a と b は別々の _count を持ちます。

static

static を付けたメソッドやフィールドは、インスタンスではなくクラスそのものに属します。new せずに クラス名.メソッド名 で呼べます。

OsdClockLogic.Format(t);   // static メソッド。new OsdClockLogic() は要らない

static なフィールドはプログラム全体で 1 つしかありません。どこからでも書き換えられるので、誰がいつ変えたか追えなくなります。値を持たない static メソッドは安全ですが、static な状態は少ないほど良いとされます。

public と private（カプセル化）

修飾子誰が使えるか
privateそのクラスの中だけ
internal同じアセンブリ（9 章）の中だけ
publicどこからでも

上の Counter では _count が private です。外からは Add() で 1 増やすことしかできません。_count = -5 のような、ありえない値を外から入れられません。

このように、データを隠して決まった操作だけを外に出すことをカプセル化と呼びます。クラスが自分のデータの正しさを自分で守れます。

プロジェクトの規約に「public フィールド禁止」とあるのはこのためです。

プロパティ

public int Count => _count; はプロパティです。外からはフィールドのように a.Count と読めますが、中身はメソッドです。読み取り専用の口を作るのによく使います。

class と struct

struct もデータと処理をまとめた型です。違いは渡し方です。

  • class は参照型。変数に入っているのは実体の場所。代入すると同じ実体を 2 つの変数が指す
  • struct は値型。変数に実体そのものが入る。代入すると中身がコピーされる
var a = new Counter();   // class
var b = a;               // b と a は同じ Counter を指す
b.Add();                 // a.Count も 1 になる

Vector3 や DateTime は struct です。小さなデータのまとまりに使います。

確認問題

Q1. クラスとインスタンスの違いは？

クラスは型の定義。インスタンスは new でクラスから作った実体で、それぞれが自分のフィールドを持つ。

Q2. フィールドを private にして、操作をメソッドだけに絞る利点は？

ありえない値を外から入れられなくなる。データの正しさをクラスが自分で守れる。

Q3. static な状態が少ないほうが良いのはなぜ？

どこからでも書き換えられるので、誰がいつ変えたかを追えなくなるから。

6. 継承とインタフェース

継承

既存のクラスの機能を引き継いで新しいクラスを作ることを継承と呼びます。元のクラスを基底クラス（親）、新しいクラスを派生クラス（子）と呼びます。

// Assets/Scripts/Streaming/ScreenOsd.cs:34
public sealed class ScreenOsd : MonoBehaviour

: MonoBehaviour は「MonoBehaviour を継承する」という意味です。MonoBehaviour は Unity が用意したクラスで、継承すると Unity の物体に貼り付けて動かせるようになります（7 章）。

sealed は「このクラスをさらに継承させない」という印です。

インタフェース

インタフェースは「このメソッドを持っていること」という約束だけを書いた型です。中身の処理は書きません。

public interface IResettable
{
    void ResetRun();
}

public class BgmDirector : IResettable
{
    public void ResetRun() { /* BGM を初期状態に戻す */ }
}

使う側は相手の具体的なクラスを知らなくても、IResettable として ResetRun() を呼べます。

foreach (IResettable r in all) r.ResetRun();

この IResettable は説明用で、廻リ視には無い。廻リ視には ResetRun を持つクラスが 19 個あるが、共通のインタフェースが無いので、まとめて呼ぶことができない。前回の調査で一番重い課題とした点はここにつながる。

継承よりインタフェース

C# では基底クラスを 1 つしか持てません。インタフェースはいくつでも実装できます。また継承は親の中身に強く縛られます。そのため「機能を共有したいだけなら、継承より小さなインタフェースや、別クラスを持たせる形を選ぶ」のが一般的な指針です。

確認問題

Q1. class A : MonoBehaviour の : は何を表す？

A が MonoBehaviour を継承していること。

Q2. インタフェースがあると何ができる？

具体的なクラスを知らなくても、約束したメソッドを呼べる。違うクラスをまとめて同じように扱える。

7. Unity の仕組み

GameObject とコンポーネント

Unity のシーンに置く物体はすべて GameObject です。GameObject 自体は位置と名前しか持ちません。

機能はコンポーネントとして GameObject に貼り付けます。カメラ、音源、見た目のメッシュ、そして自分で書いた MonoBehaviour のクラスも、すべてコンポーネントです。

1 つの GameObject に複数のコンポーネントを貼れます。たとえば廻リ視のシーンには [Tracker] という GameObject があり、そこに PlayerZoneTracker などが貼られています。

MonoBehaviour は new しない

普通のクラスは自分で new します。MonoBehaviour は違います。シーンに貼ってあれば、シーンを開いたときに Unity がインスタンスを作ります。コードから足すときは AddComponent<T>() を使います。

Unity が呼ぶメソッド

MonoBehaviour に決まった名前のメソッドを書くと、Unity が決まった時に呼びます。

メソッド呼ばれる時
Awake()インスタンスが作られた直後に 1 回
Start()最初のフレームの前に 1 回
Update()毎フレーム
LateUpdate()毎フレーム、全員の Update の後
OnDestroy()消される時

自分では呼ばず、Unity に呼ばれる。この形は「制御の反転」と呼ばれます。自分のコードが主導権を持たないので、どのコンポーネントの Update が先に呼ばれるかは基本的に決まっていない点に注意が要ります。

SerializeField と Inspector

// Assets/Scripts/Tracking/PlayerZoneTracker.cs
[SerializeField] private float hysteresisShrink = 0.15f;

[SerializeField] を付けた private フィールドは、Unity の画面（Inspector）に表示され、そこで値を変えられます。変えた値はシーンのファイルに保存されます。

注意点があります。シーンに保存された値は、コードの初期値（ここでは 0.15f）より優先されます。コードの初期値を直しても、シーンに古い値が保存されていれば古い値で動きます。

他のコンポーネントを手に入れる 3 つの方法

方法書き方性質
Inspector で繋ぐ[SerializeField] private CameraSwitchDirector? director;誰が誰を使うかがフィールドの宣言で見える
同じ GameObject から取るGetComponent<T>()範囲が狭く、速い
シーン全体から探すFindObjectOfType<T>()どこからでも探せるが遅い。誰が誰を使うかがコードを読まないと分からない

廻リ視には 3 つ目が 210 か所あります。10 章で詳しく扱います。

確認問題

Q1. GameObject とコンポーネントの関係は？

GameObject は物体の入れ物で、機能はコンポーネントとして貼り付ける。MonoBehaviour のクラスもコンポーネントの 1 つ。

Q2. SerializeField の初期値を直したのに挙動が変わらない。何を疑う？

シーンや prefab に古い値が保存されていて、そちらが優先されていること。

Q3. Update の中で毎フレーム FindObjectOfType を呼ぶと何が困る？

シーン全体を毎フレーム探すので重い。1 フレーム 11 ミリ秒の予算を食う。

8. イベント

あるクラスで何かが起きたとき、それを知りたい別のクラスへ知らせる仕組みがイベントです。

// 知らせる側 — Assets/Scripts/Tracking/PlayerZoneTracker.cs
public event Action<PlayerZone?, PlayerZone>? ZoneChanged;

// ゾーンが変わったら
ZoneChanged?.Invoke(oldZone, newZone);
// 知りたい側 — Assets/Scripts/Tracking/ZoneLayoutApplier.cs:54
tracker.ZoneChanged += OnZoneChanged;     // 登録（購読）する

private void OnZoneChanged(PlayerZone? oldZone, PlayerZone newZone)
{
    // ゾーンが変わったときの処理
}

Action<A, B> は「A と B を受け取って何も返さない関数」の型です。+= で登録し、-= で解除します。?.Invoke は「登録者がいれば呼ぶ」です。

イベントの利点

知らせる側は、誰が聞いているかを知りません。PlayerZoneTracker は、周を数えるクラスがあることも、配置を直すクラスがあることも知らずに済みます。聞く側を増やしても、知らせる側を直す必要がありません。

イベントの注意点

  • 解除を忘れる。聞く側が消えても登録が残ると、消えた相手を呼んでエラーになる。OnDestroy で -= する
  • 順番が見えない。登録者が複数いると、どの順で呼ばれるかがコードから読みにくい
  • 引数の意味が位置でしか分からない。廻リ視の CameraEntered は Action<int,int,int> で、3 つの int のどれが何かは型からは分からない。名前付きの struct にまとめると取り違えにくい

確認問題

Q1. イベントを使うと、知らせる側のクラスにとって何が良い？

誰が聞いているかを知らずに済む。聞く側を増やしても、知らせる側を直さなくてよい。

Q2. Action<int,int,int> のイベントの問題は？

3 つの int の意味が順番でしか分からず、取り違えてもコンパイルが通る。

9. コードのまとまり

コードは小さい単位から順に、次のようにまとまっています。

単位中身廻リ視の例
メソッド処理 1 つFormat

namespace FixedCamVr.Streaming

    public sealed class OsdClockLogic { ... }

別の名前空間から使うときは、ファイルの先頭に using FixedCamVr.Streaming; と書きます。

アセンブリ

アセンブリには 2 つの役割があります。

  1. 依存の許可。.asmdef に「どのアセンブリを使ってよいか」を書く。書いていないアセンブリのクラスを使うとコンパイルエラーになる。循環（A が B を使い、B も A を使う）は作れない
  2. コンパイルの単位。変えたアセンブリと、それに頼るアセンブリだけを再コンパイルする

廻リ視のアセンブリの依存はこうなっています。

Diagnostics ──→ Tracking ──→ Streaming
     └──────→ Input
OvrBridge（asmdef なし）──→ 全部

Streaming は Tracking を使えません。だから Streaming のクラスは Tracking のクラスを型として書けず、Behaviour（全コンポーネント共通の親）や Func（関数の型）でぼかして受け取っています。これが前回の調査で「依存の向きが歪んでいる」とした箇所です。

確認問題

Q1. 名前空間とアセンブリの違いは？

名前空間はクラス名の住所で、コンパイルの区切りではない。アセンブリはコンパイルの単位で、使ってよい相手を宣言で縛れる。

Q2. アセンブリ A が B を使っているとき、B が A を使うとどうなる？

循環になるので、Unity はコンパイルできない。

10. 依存と設計の原則

依存

クラス A がクラス B を使っているとき、「A は B に依存している」と言います。B を変えると A が壊れる可能性があります。

依存はゼロにできません。目標は次の 3 つです。

  • 依存の数を減らす
  • 依存の向きを揃える（変わりやすいものが、変わりにくいものに頼る）
  • 依存が宣言から見えるようにする

結合度と凝集度

結合度
クラス同士がどれだけ互いに頼り合っているか。低いほど良い。1 つ直したときの影響が狭くなる。
凝集度
1 つのクラスの中身が、どれだけ同じ目的に向いているか。高いほど良い。何をするクラスかが一言で言える。

廻リ視の ShowControlClient（3,656 行）は、設定の読み込み・通信・各所への配布・報告の受付・値の中継を全部持っています。凝集度が低く、31 クラスから頼られているので結合度が高い状態です。

単一責任の原則

「1 つのクラスが変わる理由は 1 つにする」という原則です。ShowControlClient は、通信方式が変わっても、報告の仕様が変わっても、設定の形が変わっても直すことになります。変わる理由が多すぎます。

依存を外から渡す

必要な相手を自分で探すのではなく、外から渡してもらう形を依存性の注入（Dependency Injection、DI）と呼びます。

// 自分で探す（廻リ視に多い形）
var timeline = FindObjectOfType<TimelineDirector>();

// 外から渡してもらう
[SerializeField] private TimelineDirector? timeline;   // Inspector か、シーンを組むコードが入れる

外から渡す形には 3 つの利点があります。

  1. フィールドを見れば、このクラスが誰に頼っているかが分かる
  2. 探す処理が無いので速い
  3. テストで、本物の代わりに試験用の相手を渡せる

その他の原則

DRY（Don't Repeat Yourself）
同じ知識を 2 か所に書かない。片方だけ直して食い違うから。廻リ視ではリセットの呼び出しの並びが 4 か所に書き写され、1 か所で音のリセットが抜けている。
YAGNI（You Aren't Gonna Need It）
今要らない機能を先回りして作らない。使われない仕組みは、読む手間と壊れる場所を増やすだけになる。
関心の分離
違う種類の仕事を別の場所に置く。廻リ視の「判断は Logic、画面への反映は MonoBehaviour」がこの例。

確認問題

Q1. 結合度と凝集度は、それぞれ高い方が良い？低い方が良い？

結合度は低い方が良い。凝集度は高い方が良い。

Q2. FindObjectOfType で探す形と、SerializeField で渡す形の違いを 2 つ挙げて。

渡す形は、誰に頼っているかがフィールドで見える。探す処理が無いので速い。テストで試験用の相手を渡せる。（このうち 2 つ）

Q3. リセットの並びが 4 か所にあることは、どの原則に反している？

DRY。同じ知識を複数の場所に書いたので、1 か所だけ直し忘れて食い違った。

11. テスト

テストとは

テストは「このコードがこう動くはず」を確かめるコードです。一度書けば、何回でも自動で確かめられます。

関数やクラスを 1 つずつ確かめるテストを単体テスト（ユニットテスト）と呼びます。廻リ視には約 2,300 件あります。

実際のテスト

// Assets/Tests/Streaming/OsdClockLogicTests.cs
[Test]
public void Format_MatchesTheReferenceShot()
{
    Assert.AreEqual("2026/09/06 14:23:45",
                    OsdClockLogic.Format(new DateTime(2026, 9, 6, 14, 23, 45)));
}
  • [Test]：このメソッドがテストだという印
  • Assert.AreEqual(期待値, 実際の値)：2 つが等しくなければテストを失敗にする
  • メソッド名：何を確かめるかを文として書く

テストは 3 段で書くのが基本です。準備する（Arrange）、実行する（Act）、確かめる（Assert）。

なぜテストを書くのか

  1. 壊したことにすぐ気づける。別の場所を直したせいで前の機能が壊れることをデグレード（退行）と呼ぶ。テストがあれば直した直後に分かる
  2. 安心して作り直せる。中の書き方を変えても、テストが通れば外から見た動きは変わっていない
  3. 仕様の記録になる。テストを読めば、そのコードがどう動くべきかが分かる

テストしやすい設計

Format がテストしやすいのは純粋関数だからです。一方、MonoBehaviour のテストは難しくなります。Unity の起動、シーンの用意、フレームが進むのを待つ必要があるからです。

そこで廻リ視は、判断を Logic クラスに寄せ、MonoBehaviour は値を集めて渡すだけにしています。

ScreenOsd（MonoBehaviour）           OsdClockLogic（Logic）
  毎フレーム Update()                    Format(時刻) → 文字列
  今の時刻を読む          ──渡す──→      NeedsRedraw(時刻, 前回) → bool
  返ってきた文字を画面に描く ←─返す──

テストは右側だけを確かめます。左側はほとんど判断をしないので、壊れる余地が小さくなります。この分け方を Humble Object パターンと呼びます。

テストで分からないこと

テストが確かめるのは、書いた条件だけです。画面にどう見えるか、実機で間に合うか、怖いかは確かめられません。廻リ視が実機の録画（quest-record.py）を別に持っているのはこのためです。

自分で見る

Unity のテストはこのコマンドで全部回ります。数分かかります。

.\tools\unity.ps1 test

Assets/Tests/Streaming/OsdClockLogicTests.cs を開き、テスト名だけを上から読んでください。時刻表示の仕様が読み取れるはずです。

確認問題

Q1. デグレードとは？

別の箇所を直したせいで、以前動いていた機能が壊れること。

Q2. Logic クラスがテストしやすい理由は？

Unity に頼らず、値を引数で受けて戻り値で返すから。Unity を起動せずに、好きな値を渡して結果を確かめられる。

Q3. テストが全部通れば、体験は正しく動いていると言える？

言えない。テストは書いた条件だけを確かめる。見た目・実機の性能・体験の質は別の方法で確かめる。

12. Git

Git とは

Git はファイルの変更履歴を記録する道具です。いつ、誰が、何を、なぜ変えたかが残り、いつでも前の状態に戻せます。

用語

リポジトリ
履歴を記録しているフォルダ全体。廻リ視なら fixed-cam-vr。
コミット
変更を 1 まとまりとして履歴に記録すること。記録したもの自体もコミットと呼ぶ。各コミットには 8505a557 のような番号（ハッシュ）が付く。
ステージ（add）
次のコミットに含めるファイルを選ぶこと。
ブランチ
履歴の枝。本流（master）を壊さずに、別の枝で作業できる。今の作業ブランチは feature/tablet-ui-motion。
マージ
枝の変更を別の枝へ取り込むこと。
リモート
GitHub など、別の場所にあるリポジトリの写し。origin と呼ぶことが多い。
push / pull
push は手元のコミットをリモートへ送る。pull はリモートのコミットを手元へ取り込む。
コンフリクト
2 つの枝が同じ行を別々に変えていて、自動で取り込めない状態。人が選んで直す。

基本の流れ

git status                      # 何が変わっているか見る
git diff                        # 変わった中身を見る
git add <ファイル>              # コミットに含めるファイルを選ぶ
git commit -m "fix：〇〇を修正"  # 記録する
git push origin <ブランチ名>     # GitHub へ送る

良いコミットの条件

  • 1 つのコミットに 1 つの目的。関係ない変更を混ぜない
  • メッセージで「何を変えたか」が分かる。このプロジェクトは 種類：日本語の要約 の形
  • コミットした時点で動く状態にする

自分で見る

git log --oneline -10

直近 10 件のコミットが出ます。どれか 1 つの番号を選んで、次を打つと、そのコミットで何が変わったかが見えます。

git show --stat <番号>

確認問題

Q1. ブランチを切って作業する利点は？

本流を壊さずに作業できる。うまくいかなければ枝ごと捨てられる。

Q2. コミットに関係ない変更を混ぜると何が困る？

後で片方だけ取り消したくなったとき、分けて戻せない。履歴を読んでも何の変更か分からない。

13. デバッグの手順

プログラムが期待どおりに動かない原因（バグ）を探して直すことをデバッグと呼びます。思いつきで直すと、別の場所を壊したり、直ったように見えて残ったりします。手順で進めます。

  1. 症状を正確に書く。「動かない」ではなく「2 人目の体験者のとき、導入で音が鳴らない」
  2. 再現する。毎回起こせる手順を見つける。再現できないものは、直ったかどうかも確かめられない
  3. 範囲を絞る。どこまでは正しく、どこからおかしいかを見つける。廻リ視なら、配信のスマホ／ネットワーク／Unity／Meta XR／ビルドのどこか（troubleshoot スキルがこの順に切り分ける）
  4. 仮説を立てて確かめる。「リセットが音の状態を戻していないのでは」→ ログで確かめる
  5. 直す。原因を直す。症状だけを隠さない
  6. 再発を防ぐ。同じバグを捕まえるテストを書く

ログ

プログラムの途中で状況を書き出すのがログです。

Debug.Log($"[XP] ev=seg lap={lap} cam={cam}");

$"..." の中の {lap} には変数の値が入ります。廻リ視は [XP] で始まるログを決まった形で出し、tools/analyze-xp-log.py が自動で読んで、体験が正しく進んだかを判定します。

観測を疑う

ログが出ていないことは、処理が起きていない証拠になりません。ログを出す側が壊れていることもあります。廻リ視には「ログは全部正常なのに、実機の画には何も出ていなかった」事故が何度も記録されています。結論の前に、別の手段（録画など）で同じ場面を確かめます。

確認問題

Q1. 再現手順を先に見つけるのはなぜ？

再現できなければ、直したあとに直ったかを確かめられないから。

Q2. バグを直したあとにテストを書くのはなぜ？

同じバグが戻ってきたときに、自動で気づけるようにするため。

14. ビルドと実機

ビルド
ソースコードと素材から、配布できる実行ファイルを作ること。廻リ視は .\tools\unity.ps1 build fixedcam で Builds/mawarimi.apk を作る。
Development Build と Release
開発用はログやデバッグ機能を含む。提出・展示用の Release は含まない分、軽い。
IL2CPP / ARM64
C# を C++ に変換してから、Quest の CPU（ARM64）用にコンパイルする方式。実機で速く動く代わりにビルドが遅い。
adb
Android Debug Bridge。PC から USB で Android 端末（Quest を含む）を操作する道具。adb install でアプリを入れ、adb logcat で端末のログを読む。
CLI
Command Line Interface。画面のボタンではなく、コマンドを打って操作する方式。手順を文字で残せて、自動化できる。廻リ視は Unity の操作をすべて tools/unity.ps1 の CLI に集めている。

Editor と実機の違い

Unity の Editor で動いても、実機で同じに動くとは限りません。廻リ視で実際に起きた例です。

  • 実行時に名前で探すシェーダが、ビルドで外されて実機だけ画が出ない
  • パススルー（現実の部屋の映像）は実機にしか無い
  • 実機は PC より遅いので、Editor では間に合う処理が間に合わない

だから最後は実機で確かめます。

確認問題

Q1. Editor で動いたのに実機で動かない。理由として考えられるものを 2 つ。

ビルドでファイルやシェーダが外れた。実機にしか無い機能（パススルー等）が関わっている。実機の性能が足りない。（このうち 2 つ）

15. ネットワーク

廻リ視は、スマホが撮った映像を Wi-Fi で Quest へ送っています。この仕組みを理解するための用語です。

IP アドレス
ネットワーク上の機器の番号。192.168.1.23 の形。家庭や会場の Wi-Fi では、ルーターが接続のたびに配ることが多く（DHCP）、同じ機器でも番号が変わりうる。
ポート
1 台の機器の中で、どのプログラム宛てかを区別する番号。192.168.1.23:8090 の 8090。
サーバとクライアント
サービスを提供する側がサーバ、使う側がクライアント。廻リ視ではスマホが映像のサーバ、Quest がクライアント。
HTTP
Web で使う通信の約束事。クライアントが「これをください」（リクエスト）と送り、サーバが返す（レスポンス）。
JSON
データを文字で表す形式の 1 つ。{"totalLaps": 3, "lang": "ja"} のように書く。廻リ視の体験の設定 show.json はこの形式。
MJPEG
JPEG の静止画を次々に送ることで動画にする方式。仕組みが単純で、受け取った 1 枚ずつをすぐ表示できる。
遅延
カメラが撮ってから画面に出るまでの時間。廻リ視は 100 ミリ秒以内を目標にしている。

確認問題

Q1. 昨日まで繋がっていたスマホに今日繋がらない。最初に疑うことは？

IP アドレスが変わったこと。DHCP で配られた番号は接続のたびに変わりうる。

16. 非同期処理

ファイルの読み込みや通信は、終わるまでに時間がかかります。その間プログラム全体を止めると、VR では画面が固まり、酔いの原因になります。

そこで「待っている間に他の処理を進め、終わったら続きをやる」書き方をします。これを非同期処理と呼びます。C# では async と await を使います。

// Assets/Scripts/Streaming/BgmDirector.cs（整えた）
private async Task StartTrackAsync(ShowBgmDef def)
{
    AudioClip? clip = await LoadClipAsync(track.url);   // 読み込みが終わるまで、ここで「待つ」
    // ここから先は、読み込みが終わってから実行される
}
  • async：このメソッドの中で await を使うという印
  • await：処理の終わりを待つ。待っている間、Unity は他のフレームを描き続ける
  • Task：「いつか終わる処理」を表す型

注意点

  • 待っている間に状況が変わる。読み込み中に体験者が交代しているかもしれない。続きを実行する前に、まだ必要かを確かめる。中止の合図には CancellationToken を使う
  • 例外が消える形がある。async void にすると、中で起きたエラーを呼び出し側が受け取れない。async Task にする（廻リ視の async void は 0 件）

確認問題

Q1. 通信を非同期で書かないと、VR では何が起きる？

通信が終わるまで画面の描き直しが止まり、画面が固まる。酔いにつながる。

17. 設計の流儀（レイヤ・DDD）

ここまでの原則を、大きなプログラム全体の形にまとめた考え方がいくつかあります。代表的な 2 つを説明します。

レイヤードアーキテクチャ

コードを役割で層に分け、上の層が下の層だけを使うようにする形です。

層役割廻リ視で近いもの
表示層画面に出す・入力を受けるScreenOsd、CommsPanel
アプリケーション層処理の順番を組み立てるShowRunDirector、TakeRunner
ドメイン層体験のルールそのものShowRunLogic、TakeRunnerLogic
インフラ層通信・ファイル・外部機器MJPEG の受信、show.json の読み込み

大事なのは、ドメイン層が他のどの層にも頼らないことです。ルールが画面や通信の都合で変わらなくなり、テストもしやすくなります。

DDD（ドメイン駆動設計）

ドメインは、そのソフトウェアが扱う対象の世界です。廻リ視なら「体験」「周」「区間」「人形」「来場者」の世界です。

DDD は、そのドメインの言葉と規則をそのままコードの型と構造にする流儀です。主な道具は次のとおりです。

ユビキタス言語
開発者と作り手が同じ言葉を使い、その言葉をそのままクラス名・メソッド名にする。廻リ視の「周」「区間」「take」はこれに近い。
値オブジェクト
意味ごとに小さな型を作る。「進行の周」と「区間の周」を別の型にすれば、取り違えはコンパイルエラーになる（2 章の問題の解決）。
エンティティ
番号で区別され、時間とともに状態が変わるもの。廻リ視なら「来場者」「体験 1 回（ラン）」。
集約
一緒に正しさを保つべきデータのまとまりと、その持ち主。外からは持ち主を通してだけ変える。廻リ視なら「体験 1 回ぶんの状態」を 1 つの持ち主にまとめ、リセットもそこを通す（前回の課題 1 の解決）。
リポジトリ
データの保存と取り出しを隠す窓口。ドメイン層が「どこに保存されるか」を知らずに済む。

流儀は道具であって目的ではない

DDD は、規則の多い業務システムを長く保守するために生まれました。小さなプログラムに全部を入れると、層と型が増えるだけで得るものが少なくなります。

前回の調査では、廻リ視には DDD を全面的には入れず、値オブジェクトと集約の考え方だけを借りると判断しました。設計の流儀は、今のコードで実際に起きている問題を解決するかどうかで選びます。

確認問題

Q1. ドメイン層が他の層に頼らないと何が良い？

ルールが画面や通信の都合で変わらなくなる。Unity や通信無しでテストできる。

Q2. 「進行の周」と「区間の周」を別の型にするのは、DDD のどの道具？

値オブジェクト。

Q3. 小さなプログラムに DDD を全部入れない理由は？

層と型が増えて読む量と直す場所が増えるのに、解決する問題が少ないから。
