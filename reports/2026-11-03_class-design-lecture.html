廻リ視のクラス設計を読む

2026-11-03。11-02 の「エンジニアリングの基礎」の続き。基礎の 5 章（クラス）、8 章（イベント）、9・10 章（コードのまとまりと依存）、17 章（DDD）を、廻リ視の実際のクラスに当てはめる。数はこの日のコードで数えた。

廻リ視のクラス設計は、9 つの考え方で読めます。箱の依存の向き、判断と Unity の部品の分け方、1 クラス 1 役目、2 種類の周、値オブジェクト、イベント、リセットの経路、名前、テストです。どれも、11-03 の作業で実際に直した場所を例にしています。

1. この資料の地図

下の図は、この資料で扱う考え方を 6 つの枝に分けたものです。章の番号は本文の見出しと同じです。

先に、この資料で使う言葉を並べます。

言葉意味

2. 箱と依存の向き

廻リ視の実行時のコードは、6 つの箱（アセンブリ）に分かれています。図 2 の矢印は「使う」の向きです。

読み方

  • 矢印は下向きだけです。Streaming はどの箱も使いません。
  • Input と Fx は、ほかのどの箱も使いません。
  • OvrBridge は asmdef を持たないので、Unity の既定の箱（Assembly-CSharp）に入ります。この箱は全部の箱を使えます。Meta XR SDK に触れるのはここだけです。

向きを決める理由

Unity は、箱どうしが互いを使う形（循環）を許しません。コンパイルが通りません。

向きが一方なら、下の箱は上の箱を知らずにテストできます。Streaming のテストは、Tracking や Diagnostics を用意せずに書けます。

向きに逆らう用事の扱い

Streaming の ShowControlClient は、卓へ送る heartbeat に「いま何周目か」を載せます。周を数えているのは上の箱の Tracking にある LapCounter です。Streaming から Tracking は使えません。

そこで、Tracking の側が起動時に「周回数を返す関数」を Streaming に渡します。

// Tracking/LapCounter.cs（上の箱）
showControl.ProgressLapProvider = () => _logic.ProgressLap;

// Streaming/ShowControlClient.cs（下の箱）
public Func<int>? ProgressLapProvider;
hb.lap = ProgressLapProvider != null ? ProgressLapProvider() : -1;

Streaming が知っているのは「int を返す関数」だけで、LapCounter という型は知りません。ShowControlClient には、このような中継口が 18 個あります。

代償もあります。型の上では繋がっていないので、値がどこから来るかを知るには、関数を代入している場所を探す必要があります。

部品が相手を探す

実行時のコードには FindObjectOfType が 219 か所あります。シーン全体から型で相手を探す命令です。手軽ですが、誰が誰を使っているかがクラスの宣言から見えません。新しく読む人が依存を追いにくい原因の 1 つです。

Q1. Streaming が Tracking を直接使えないのはなぜか。
Tracking が Streaming を使っているから。互いに使うと循環になり、Unity はコンパイルを通さない。
Q2. 中継口（Func）の代償は何か。
型の上で繋がっていないので、値の出どころをコードの宣言から追えない。関数を代入している場所を探す必要がある。

3. 判断と Unity の部品を分ける

MonoBehaviour は Unity が無いと動きません。そこで、判断の部分だけを Unity を使わないクラスに移し、MonoBehaviour はそれを呼ぶだけにします。

実際のコードでは、ShowRunDirector が毎フレーム入力を集めて ShowRunLogic.Tick に渡します。

// Streaming/ShowRunDirector.cs
ShowRunEvent ev = _logic.Tick(ShowClock.Dt, atStart, takeRunning,
                              introCompleted, introAborted, ...);

Tick は「経過秒・スタート区画に居るか・演出が走っているか」などを受け取り、「本編が始まった」「体験が終わった」などの出来事を返します。ShowRunLogic は画面も音も触りません。

置き場入れるもの例
Logic（純粋な C#）判断。入力から答えを決めることいつ本編へ移るか・周の数え方・終わり方の判定
MonoBehaviourUnity との出入り部品を探す・時計を読む・画面と音に反映する

廻リ視には名前の末尾が Logic のクラスが 63 個あり、名前が 〜LogicTests のテストファイルが 55 個あります。テストは約 2,300 件あります。Unity をバッチで起動して回しますが、シーンも実機も使いません。

この分け方には Humble Object パターンという名前があります。Unity の側を、判断を持たない薄い部品にしておく方法です。

図 3 の右のテストは Unity をバッチで起動して回りますが、シーンも部品も用意しません。ShowRunLogic を new して Tick を呼ぶだけです。

Q1. 判断を MonoBehaviour の中に書くと、何が困るか。
テストするのに Unity が要る。シーンと部品を用意しないと判断を確かめられない。
Q2. 「周を数える」は Logic と MonoBehaviour のどちらに置くか。
Logic。入力（どのカメラの区画に入ったか）から答え（何周目か）を決める判断なので。実際に LapCounterLogic が持っている。

4. 1 つのクラスに 1 つの役目

クラスを変える理由が 1 つだけになるように分ける、という原則があります。単一責任の原則と呼びます。役目が多いクラスは、1 か所を直すと関係のない役目まで壊すことがあり、読む人も全体を読まないと目的の場所にたどり着けません。

クラス行数持っている役目
ShowControlClient2,781（5 ファイル）設定・卓との通信・リセット・報告・中継口
CommsPanel2,592スイの連絡の面
TakeRunner1,872演出を画面へ適用する
ShowTelemetryHost1,802検証用のログ
ShowCgLayer1,678CG の人形の合成

行数にはコメントを含む。実行時のコードの約 27% がコメント。

11-03 に ShowControlClient（3,670 行）を役目ごとのファイルに分けました。

partial は、1 つのクラスを複数のファイルに分けて書く C# の機能です。コンパイルすると 1 つのクラスに戻ります。Unity から見た部品も 1 つのままなので、シーンの設定は何も変わりません。

限界もあります。ファイルは分かれましたが、役目どうしは同じクラスの変数を共有したままです。本当に分けるには、別々のクラスにして、必要な値だけを受け渡す形にする必要があります。そうしなかったのは、部品が増えるとシーン（Main.unity）の組み直しが要り、いまそのファイルには別の作業の変更が載っているためです。

Q1. partial でファイルを分けると、何が良くなり、何が変わらないか。
読む場所がファイル名で分かるようになる。役目どうしが同じ変数を共有していることは変わらない。

5. 2 種類の周

廻リ視では A → B → C の 3 区画を 3 周します。体験者は途中で引き返すことがあります。引き返したとき、「何周目か」には 2 つの意味が生まれます。

周決まり使う所
進行の周 ProgressLap順路どおりに 1 周したときだけ増える。減らない体験が終わったかの判定
区間の周 SegmentLapいま居る区画に、前に居たときの周。引き返すと戻るその区画の演出・録画・BGM・滞在の計測

取り違えると、次のことが起きます。

  • 終了判定に区間の周を使うと、最後の A で引き返した人の周が戻り、体験が終わらない。
  • 演出に進行の周を使うと、引き返した C で 2 周目 C の演出が先に出てしまう。1 回だけ出す設定（once）の演出は、本当に 2 周目の C に来たときにはもう出ない。

11-03 まで、どちらの周も CurrentLap という同じ名前で呼ばれていました。クラスによって意味が逆でした。いまは名前で区別しています。

Q1. 図 5 の右端（B）で、2 つの周がどちらも 2 なのはなぜか。
引き返した後で順路（A → B）に戻ったので、区間の周も 2 周目の区画として数えられるから。
Q2. 体験の終了判定に使うのはどちらか。
進行の周。減らないので、引き返しても終わりが遠のかない。

6. 値オブジェクト

値オブジェクトは、値そのものを表す小さな型です。基礎の 5 章の struct を、次の 4 つを守って使います。

性質意味
中身で比べる中身が同じなら同じものとして扱う。「どの実体か」は問わない
作った後に変えない中身を変えたいときは新しく作る。C# では readonly struct と書く
意味のある名前を持つ型の名前と各値の名前で、何を表しているかが分かる
正しくない値を作らせない作るときに範囲などを確かめる

11-03 に、区画へ入ったという知らせを値オブジェクト SegmentEntry にしました。

// Streaming/CueScheduler.cs
public readonly struct SegmentEntry
{
    public readonly int Camera;       // 区画のカメラ番号（A = 0）
    public readonly int SegmentLap;   // 区間の周
    public readonly int ProgressLap;  // 進行の周
    public SegmentEntry(int camera, int segmentLap, int progressLap) { ... }
}

// 作る側は、名前を付けて渡す
cueScheduler.NotifyCameraEntered(
    new SegmentEntry(camera, segmentLap: segLap, progressLap: _logic.ProgressLap));

前は int を 3 つ並べていたので、2 つ目と 3 つ目を入れ違えてもコンパイルが通りました。どちらも int だからです。いまは受け取る側が entry.SegmentLap と名前で読みます。

SegmentEntry はまだ 4 つ目の性質（正しくない値を作らせない）を持っていません。周が 0 以下でも作れます。

廻リ視の中の例

型種類理由
SegmentEntry値オブジェクトカメラと 2 つの周の組。作った後に変えない
ShowBodyInput値オブジェクト体験者の頭と手の姿勢の組（readonly struct）
Vector3値オブジェクトUnity の位置。中身が同じなら同じ位置
ShowEndingOutcome列挙型（enum）帰還 End・人形 End・中断のどれか。種類を表す
ShowRunDef などデータを運ぶだけの型show.json を読むための型。JsonUtility が書き込むので変えられる形にしてある
体験者・カメラ値ではない中身が変わっても同じ人・同じカメラ。DDD ではエンティティと呼ぶ

まだ値オブジェクトにしていない所

周そのものは、いまも int です。区間の周と進行の周を別々の型にすれば、取り違えはコンパイルで止まります。まだしていないのは、周が show.json・ログ・演出の ID（L2C1#0）など多くの場所で数として計算・保存されていて、変える範囲が広いからです。11-03 は、取り違えが実際に起きやすかった受け渡しの 1 か所（SegmentEntry）から始めました。

Q1. 値オブジェクトと、ただの int の違いを 1 つ挙げよ。
名前と型を持つので、別の意味の値と取り違えたときにコンパイルで止まる。
Q2. show.json を読む ShowRunDef が値オブジェクトでないのはなぜか。
JsonUtility が外から値を書き込むので、作った後に変えない形にできないから。データを運ぶだけの型として扱う。

7. イベントで知らせる

体験者が区画に入ると、何人もの部品がそれを知りたがります。CueScheduler は、その知らせをイベント CameraEntered で配ります。

CueScheduler は、誰が受け取るかを知りません。受け取りたい部品が自分で購読します。購読する部品を足しても、CueScheduler は変えなくて済みます。

導入の途中は、ここで知らせを止めます。止める場所が 1 か所なので、演出・録画・BGM・滞在がまとめて止まります。部品ごとに「導入中なら何もしない」と書くと、どれか 1 つを書き忘れます。

気をつけること

  • 受け取る側は、自分に必要な値を名前で選ぶ。図 7 の右の列がその選び方。
  • 購読者が呼ばれる順番に頼らない。C# は購読した順に呼ぶが、Unity は部品どうしの OnEnable の順番を保証しない（Script Execution Order で指定しない限り）ので、購読の順番も決まらない。
  • イベントの名前は、実際に発火する場面と合わせる。周を数え直す合図は、11-03 まで RunReset という名前で、「体験者が替わった」と読めた。実際には導入から本編へ移るときにも発火する。いまは LapCountReset（周の数え直し）と呼ぶ。
Q1. 購読者を足しても CueScheduler を変えなくてよいのはなぜか。
CueScheduler は配り先を知らず、受け取りたい側が自分で購読するから。
Q2. LapCountReset を「体験者が替わった合図」として購読すると、何が起きるか。
導入から本編へ移るときにも発火するので、そこで 1 人目の録画などを消してしまう。

8. 体験 1 回ぶんの状態とリセット

展示では数十人が続けて体験します。次の人が始まる前に、前の人の状態（報告数・周・演出の済み印・録画・音・画面の劣化）を全部戻す必要があります。

②の BeginRun は、体験の進行を受け付ける門を閉じたあとで、演出と録画をもう一度落とします。門が開いたまま周を数え直すと、導入の途中に本編の演出が始まってしまうからです。順番に意味があるので、並びは変えません。

11-03 まで、①の並びは卓と現地の 2 か所に書き写されていました。部品を足したときに片方だけ書き足すと、1 人目は正常で、2 人目から壊れます。この形の不具合が 4 回起きています。いまは 1 つのメソッドにまとめ、さらにテストで書き忘れを止めます。

VisitorRunResetCoverageTests は、ソースを読んで ResetRun を持つ部品を全部拾い、次のような表と照合します。表に無い部品が見つかると落ちます。

部品落とす場所段
CueSchedulerResetForNewVisitor①
SwitchAudioCueBeginRun②
WalkGuideIntroDirector（RunRestarted の購読）③

実際の表は 27 行。

DDD には「関係するデータのまとまりに、持ち主を 1 つ置く」という考え方があり、集約と呼びます。廻リ視は DDD を全面的には使っていませんが、体験 1 回ぶんの状態を落とす並びを 1 か所にしたのは、この考え方を借りたものです。

Q1. 新しい部品に ResetRun を書いたが、どこからも呼んでいない。何が起きるか。
1 人目は正常で、2 人目から前の人の状態が残る。テストが「表に無い部品」として落とすので、ビルド前に気づける。

9. 名前と言葉を揃える

コード・文書・人が話す言葉で、同じものを同じ名前で呼ぶことを、DDD ではユビキタス言語と呼びます。11-03 の調査で、廻リ視ではここが一番ずれていると分かりました。

あなたの言葉指していたものコード
周・N 周目体験者向けは 3 周。内部は最後の A（4-A）まで数えるProgressLap / SegmentLap
カメラ配信スマホ・映像・区画の切り替わり・作品名・絵の中の視線camera（0〜2）/ cameraId（A〜C）
A / B / C区画・カメラ・右コントローラの A ボタン・案の記号区画は camera の番号
位置合わせ床の登録・録画と凍結点を揃える・カメラの較正CourseRegistration* ほか

人の言葉が 1 語で複数を指すのは普通のことです。揃えるのはコードの側です。コードの名前は 1 つの意味に絞り、人の言葉との対応は .claude/rules/glossary.md に書いてあります。

AI はコードを読むとき、名前から意味を推測します。名前が実際の仕事と違うと、その推測ごと間違えます。

名前を変えると壊れるもの

  • Unity が保存したフィールド名。シーンや prefab の値が消える。プロパティやメソッドの名前なら影響しない。
  • 文字列で書かれた名前。tools/unity.ps1 の -executeMethod、テストのアセンブリ名、ログのキー。コンパイルでは気づけない。

フォルダの Streaming は、中身の 7% しか映像の受信ではありませんが、改名していません。2 つ目の理由で壊れるものが多いからです。代わりに Assets/Scripts/README.md に実際の中身を書いてあります。

Q1. CurrentLap を ProgressLap に変えても、シーンの値が消えなかったのはなぜか。
プロパティの名前で、Unity はプロパティを保存しないから。

10. テストで設計を守る

設計の決まりは、文書に書くだけでは守られません。読み落とされるからです。廻リ視では、決まりをテストにして、破ったら落ちるようにしています。

種類何を止めるか例速さ
判断のテストLogic の答えの誤りLapCounterTests数分（Unity をバッチで起動）・実機なし
配線のテスト呼び出しの書き忘れVisitorRunResetCoverageTests同上（Unity のテストと一緒に回る）
書き手と読み手の照合ログのキーの食い違いtools/test_telemetry_contract.py1 秒未満
実機の走行画面に実際に出たかtools/quest-record.py --walk数分・実機あり

テストを作ったら、通る場合と落ちる場合の両方を試します。11-03 の終幕の報告数の照合は、それまで同じ値どうしを比べていて、何が起きても通っていました。いまのテストは、画面が正しい数を出す場合に通り、別の数を出す場合に落ちることを確かめてあります。

Q1. 同じ値どうしを比べるテストは、なぜ役に立たないか。
何が起きても一致するので、間違いがあっても落ちない。

  2. LapCounterTests の引き返しのテストを読み、図 5 の 7 列の値と照らし合わせる。
  3. ShowRunLogic.Tick の引数を並べ、どれが Unity から来る値かを分ける。
  4. SegmentEntry に 4 つ目の性質（周が 1 以上でなければ作れない）を足すとしたら、どこに何を書くかを考える。足した後、どのテストが落ちうるかも考える。
